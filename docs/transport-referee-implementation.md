# 교통 도메인 구현 계획

- 문서 버전: v2.0 / 2026-08-14
- 적용 단계: 1단계 장거리 이동, 5단계 현지 이동

파일명은 기존 링크 호환을 위해 유지한다. 독립된 Transport Referee를 만들지 않고 공통 에이전트·검증 파이프라인이 두 맥락의 교통을 다룬다.

## 1. 카테고리 경계

| 단계 | 다루는 것 | 결정 계약 |
| --- | --- | --- |
| 1 오는 길·가는 길 | 출발지별 항공·기차·버스·배, 공항/역 접근, 출도착 시간 | 장거리 이동 제안 |
| 5 날짜별 일정·현지 이동 | 방문 순서, 도보·대중교통·택시·렌터카, 대기·버퍼·피로 | 일자별 실행 제안 |

교통패스는 1단계에서 가안이 될 수 있지만 3단계 장소와 5단계 경로가 확정된 뒤 실제 이용 구간으로 다시 계산한다. 값이 바뀌면 새 계약 또는 영향 사건을 만들고 조용히 예산만 수정하지 않는다.

## 2. 공급자

| 기능 | 한국 | 일본 |
| --- | --- | --- |
| 도보·자동차 경로 | Kakao Maps, Google Routes | Google Routes |
| 대중교통 경로 | Kakao Maps | 공개 즉시 사용 공급자 미확보 |
| 도시간 열차 일정 | TAGO 조건부 | 공개 즉시 사용 공급자 미확보 |
| 좌석·운임·예약 | 미확보 | 미확보 |

Google Routes는 일본 대중교통 기계 근거로 사용하지 않는다. 일본 대중교통 경로가 없으면 Pack의 정적 안내나 사용자가 여는 지도 링크를 `advisory`로 제공할 수 있지만, live 시간·환승·막차가 필요한 일정은 `BOOKABLE`로 올리지 않는다.

## 3. 입력

- `TripCharter`: 날짜, 목표 페이스, 개인별 예산·하드 제약
- 이전 `ACCEPTED CategoryDecisionContract`
- 후보 장소·식당·숙소 좌표와 체류시간
- 출발·도착·체크인·예약 슬롯
- 걷기·계단·대중교통·택시·운전 제약
- 날씨와 우천 대안

페이스는 하루 앵커 1·2·3개만으로 계산하지 않는다. 활동시간, 이동, 대기, 식사, 휴식, 날씨, 체력, 접근성, 예비시간을 포함한다.

## 4. 경로 데이터 계약

```ts
type RouteEvidence = {
  originCandidateId: string;
  destinationCandidateId: string;
  departureAt: string;
  timezone: string;
  mode: "walk" | "transit" | "taxi" | "car" | "bike";
  durationMinutes: number | null;
  distanceMeters: number | null;
  transfers: number | null;
  fareMinor: number | null;
  provider: string;
  fetchedAt: string;
  validUntil: string | null;
  confidence: "live" | "official_static" | "estimated" | "unknown";
};
```

경로 행렬은 `matrixVersion`, 후보 집합, 출발 시간대, 이동 모드, 공급자와 조회시각을 포함한다. 후보가 바뀌거나 교통편 시간이 바뀌면 재계산한다.

## 5. `CategoryProposal`

5단계 투표 단위는 개별 이동수단이 아니라 날짜별 실행 계획이다.

- 일자·시간대별 장소 순서
- 각 장소 체류시간
- 구간별 이동수단·시간·비용·환승
- 식사·예약 슬롯
- 체크인/체크아웃·짐 보관
- 휴식·대기·우천·막차 버퍼
- 개인별 피로·도보·접근성 부담
- 총비용과 불확실성

## 6. 결정론적 검사

`FactConstraintValidator`가 최소한 다음을 검사한다.

1. 시간대와 운영·예약 슬롯 겹침
2. 이동시간 + 체류시간 + 대기시간의 물리적 가능성
3. 첫차·막차·공항·체크인/아웃 버퍼
4. 도보·계단·피로 상한과 접근성
5. 식사 간격·휴식·목표 페이스
6. 교통비·택시 예비비·패스 비용
7. 날씨에 따른 실외 슬롯과 대안
8. 경로 근거의 조회시각·만료·공급자 공백

그리디·2-opt는 후보 순서를 만드는 휴리스틱일 뿐 최종 실행 가능성 증거가 아니다.

## 7. 패스 손익

```text
개별 요금 합계
  vs 패스 가격
  + 패스 수령·개시·구간 제한 비용
  + 환승·우회·편의성 손실
```

패스 포함 관광지 입장료를 중복으로 절감액에 더하지 않는다. 3단계 장소가 바뀌면 재계산하고, 가격·유효구간이 정적 Pack 값이면 `estimated`로 표시한다.

## 8. 공정성

실행 가능한 계획만 사용자별 만족도를 계산한다. 단순 평균으로 걷기 어려운 한 사람을 희생하지 않는다. 각 만족도 벡터에 `leximin`을 적용하고 동률일 때 평균, 양보 불균형, 비용·동선·취소 가능성·근거 품질을 본다.

서브그룹 이동은 활동·식사·일부 현지 이동에서만, 영향받는 사용자가 0단계에서 위임한 인원·시간·비용·안전 범위 안에서 허용한다. 원치 않는 사람을 혼자 분리하지 않는다.

## 9. 출력과 의무

1단계 계약은 2단계에 공항/역·시각·예산·짐·접근 의무를 넘긴다. 5단계 계약은 이전 1~4단계의 모든 `obligationsForNextCategory`를 `obligationFulfillments`로 해소해야 한다.

미확인 막차·일본 대중교통·좌석·패스 가격에 의존하면 결과에 다음을 남긴다.

- `unresolvedFacts`
- `statusValidUntil`
- 사용자 확인 링크
- 확인 전 가능한 상태 상한

## 10. 검증 시나리오

1. 서울 2박 일정에서 Kakao 경로로 장소·식당·숙소 슬롯의 물리적 가능성을 검사한다.
2. 오사카 일정에서 일본 대중교통 공급자 공백이 `BOOKABLE`을 막는다.
3. 우천 시 실외 활동을 실내 대안으로 바꾸고 시간·비용을 재계산한다.
4. 교통패스 가안이 3단계 장소 변경 뒤 손해로 바뀌어 계약 의존성을 재개방한다.
5. 걷기 상한을 넘는 평균 만족도 높은 계획이 실격된다.
