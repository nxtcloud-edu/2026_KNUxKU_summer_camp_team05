- **상위 문서**: `travel-mediation-plan.md` v1.2
- **담당 라운드**: R2
- **대상 지역**: 대한민국, 일본

> **⚠️ MVP 범위 변경 (v1.1)** — 방 배정 선호를 설문에서 **수집하지 않는다.** 따라서 8장의 배정 알고리즘·배정 점수·미충족 선호 기록은 MVP 대상이 아니며, Phase 2 재도입 시의 명세로 보존한다. 상세와 근거는 [development-and-deployment.md](development-and-deployment.md) 6장.
>
> MVP에서 이 심판이 방과 관련해 판정하는 범위는 다음으로 축소된다.
>
> - 그룹 인원 수용 가능 여부
> - 객실 조합 동시 재고 (`roomCombinationVerified` — fail-closed, 20.1절)
> - 침실 분리 여부와 그로 인한 수면 리스크 서술 (개인을 특정하지 않는다)
> - 하드 제약 실격: 도미토리 불가 · 남녀 혼숙 불가 · 흡연실 불가 (설문 "절대 안 돼요"에서 계속 수집)
>
> 프라이버시 규칙(14장 방 배정 특별 규칙, 20.4절)은 **완화되지 않는다.** 수집하지 않으므로 노출할 것도 없으며, 재도입 시 동일 규칙이 그대로 적용된다.

## 1. 역할과 경계

### 1.1 왜 숙소가 가장 어려운 라운드인가

| 이유 | 설명 |
| --- | --- |
| **예산 비중이 크다** | 전체의 30~35%. 여기서 틀리면 다른 라운드가 전부 흔들린다 |
| **취소가 어렵다** | 항공보다 유연하지만, 성수기 좋은 방은 금방 사라진다 |
| **취향 충돌이 극심하다** | "잠만 자면 된다" vs "숙소가 여행의 절반" — 슬라이더 양극단 |
| **비가격 제약이 많다** | 방 배정, 코골이, 성별, 커플, 프라이버시 — 말하기 껄끄러운 것들 |
| **위치가 다른 모든 것을 결정한다** | 숙소 위치가 동선·교통비·식당 선택을 전부 제약한다 |
| **한국은 데이터가 없다** | 공개 API로 실시간 가격을 얻기 어렵다 |

### 1.2 하는 일

| # | 책무 | 산출물 |
| --- | --- | --- |
| 1 | 지역 선정 (어느 동네에 묵을 것인가) | `areaDecision` |
| 2 | 숙소 후보 조달 및 실격 심사 | `HotelCandidate[]` |
| 3 | 위치 실측 (동선 중심·역·공항까지) | `locationMetrics` |
| 4 | 방 배정안 생성 | `roomAllocation` |
| 5 | 분할 숙박 절충 설계 | `proposals[]` |
| 6 | 최종 판결 + 예약 마감 안내 | `verdict` |

### 1.3 하지 않는 일

- **예약·결제하지 않는다.** 링크아웃.
- **개인 신상(성별·연인 관계)을 추론하지 않는다.** 방 배정은 설문에서 명시적으로 수집한 정보로만 한다 (8장).
- **일자별 동선을 짜지 않는다.** 단, 숙소 위치가 동선을 제약하므로 **활동 중심점까지의 이동시간**은 반드시 실측해 판결 근거로 쓴다.

### 1.4 순서 의존성

```
R1 항공  → 도착·출발 시각 (체크인/아웃 제약), 도착 공항 (접근성 기준점)
R1 교통  → mobilityPolicy (역세권 가중치 결정)  ★ 매우 중요
              │
              ▼
        R2 숙소 심판
              │
              ▼
R3 액티비티 → 숙소 지역이 활동 후보 반경을 제약
R4 식사    → 숙소 주변 저녁 식당 우선
R5 동선    → 숙소가 매일의 시작·종점
```

**교통편 심판이 먼저 실행되는 것이 핵심이다.** "택시 위주로 다닌다"는 정책이면 역세권 프리미엄을 낼 이유가 없고, 그만큼 숙소 등급을 올리거나 예산을 아낄 수 있다.

## 2. 입출력 계약

### 2.1 입력

```typescript
interface AccommodationRefereeInput {
  pack: DestinationPack;
  dates: { start: string; end: string; nights: number };   // R0 확정
  headcount: number;
  budgetAllocated: number;                    // 숙소 항목 1인 총액 (전체 박수 합)
  arrival: { at: string; airport?: string };  // R1 항공
  departure: { at: string };
  mobilityPolicy: {                           // R1 교통
    primaryMode: 'transit' | 'taxi' | 'car' | 'walk';
    stationProximityWeight: number;           // 0.10 ~ 0.30
  };
  hardConstraints: HardConstraint[];
  roomingPreferences: RoomingPreference[];    // 8장
  styleProfiles: Record<string, Record<string, number | null>>; // 1~7, 미응답 null
  concessionCredits: Record<string, number>;
}
```

### 2.2 출력

`AccommodationVerdict` (15장). 후속 라운드에 전달:

```
→ area, coordinates       (R3 액티비티 반경, R4 식당 반경, R5 동선 기준점)
→ checkIn / checkOut      (R5 첫날·마지막날 시간 제약)
→ actualSpend             (R6 정산, Chief 예산 재배분)
→ splitStayLegs           (분할 숙박 시 이동 일정을 R5에 전달)
```

## 3. 사용 Open API 총람 — 일본

> ⚠️ 요금·쿼터·약관은 수시로 변경된다. 착수 전 각 제공자 문서를 반드시 재확인할 것.

### 3.1 핵심

| 용도 | 제공자 | 인증 | 비고 |
| --- | --- | --- | --- |
| **일본 숙소 전반 (료칸 포함)** | **Rakuten Travel API (楽天ウェブサービス)** | Application ID | 일본 로컬 커버리지 최상. **료칸은 이것 없이는 불가** |
| ↳ 빈방 검색 | `VacantHotelSearch` | 〃 | 날짜·인원·예산으로 실시간 빈방 조회 |
| ↳ 시설 검색 | `SimpleHotelSearch` / `KeywordHotelSearch` | 〃 | 지역·키워드 기반 |
| ↳ 상세 정보 | `HotelDetailSearch` | 〃 | 어메니티, 온천 유무, 조식 |
| ↳ 순위 | `HotelRanking` | 〃 | 인기 시설 보강 |
| 글로벌 호텔 시세 | **Amadeus Hotel Search v3** | OAuth2 | `GET /v3/shopping/hotel-offers`. 체인 호텔 강세 |
| ↳ 호텔 목록 | `GET /v1/reference-data/locations/hotels/by-city` | 〃 | 도시 단위 호텔 ID 확보 |
| ↳ 평판 | `GET /v2/e-reputation/hotel-sentiments` | 〃 | 감성 분석 점수 |
| 위치·사진·평점 보강 | **Google Places API** | API Key | Place Details, Photos. 모든 후보에 공통 적용 |
| 이동시간 실측 | Google Distance Matrix / Routes | API Key | 위치 스코어링의 근거 |
| 환율 | 한국수출입은행 환율 API | API Key | JPY→KRW |

| 제공자 | 상태 | 비고 |
| --- | --- | --- |

### 3.3 일본 Pack별 숙소 특성 (도메인 지식)

| Pack | 주요 지역 후보 | 심판이 반드시 고려할 것 |
| --- | --- | --- |
| `jp-osaka` | 난바·신사이바시(번화), 우메다(교통 허브), 텐노지(저렴) | 난바는 밤이 시끄럽다. 조용함 선호자가 있으면 감점. 우메다는 교토·고베 이동에 유리 |
| `jp-tokyo` | 신주쿠·시부야(번화), 우에노·아사쿠사(저렴), 도쿄역(교통) | JR 야마노테선 내부인지가 이동시간을 좌우. 신주쿠는 가성비 좋지만 특정 구역은 밤 환경이 나쁨 |
| `jp-kyoto` | 교토역 주변(교통), 기온·가와라마치(관광 중심) | 교토는 숙소가 비싸고 빨리 마감된다. **성수기(단풍·벚꽃) 경고 필수** |
| `jp-fukuoka` | 하카타(교통), 텐진(번화) | 지하철 2정거장 차이. 저렴한 편 |
| `jp-sapporo` | 삿포로역, 스스키노 | 겨울 도보 부담 → 역 직결 여부가 중요 |
| `jp-osaka-kyoto` | 분할 숙박 기본 | 오사카 2박 + 교토 1박 형태가 표준 |

**료칸 특수 처리**: 료칸은 1박 요금에 **조석식 2식이 포함**되는 경우가 많다. 이를 단순 숙박비로 비교하면 부당하게 비싸 보인다. 심판은 `mealsIncluded`를 확인해 **식사 예산에서 차감**한 실효 숙박비로 비교해야 한다. 이 계산을 놓치면 료칸은 항상 진다.

### 4.1 한국 Pack별 숙소 특성

| Pack | 지역 후보 | 고려사항 |
| --- | --- | --- |
| `kr-gangneung` | 경포·안목·강문(바다뷰), 강릉역 주변 | **바다뷰 프리미엄이 크다.** 시내 대중교통이 약해 위치가 곧 교통비 |
| `kr-busan` | 해운대(비쌈), 서면(교통), 남포동(관광) | 지하철 접근성이 핵심 |
| `kr-jeju` | 제주시, 서귀포, 애월 | 렌터카 전제이므로 역세권 무의미. **동선 중심점까지 거리**가 기준 |

## 5. 한국 숙박 데이터 공백 대응 전략

국내 숙소는 실시간 가격을 공개 API로 얻기 어렵다. 이 한계를 숨기면 신뢰가 무너지고, 과장하면 예산이 틀어진다. **정직하게 표시하되 의사결정은 가능하게** 만드는 것이 목표다.

### 5.1 3단 레이어 전략

```
[Layer 1] 후보 발굴 — TourAPI 4.0 + Google Places
          숙소의 존재·위치·타입·편의시설·평점을 확보
          → 후보 목록은 신뢰 가능

[Layer 2] 가격 추정 — 3원 접근
          (a) Amadeus로 잡히는 체인 호텔 → 실시간 가격 (confidence: "live")
          (b) 자체 시세 테이블 → 지역·타입·요일·시즌별 밴드
              (₩ 5만 미만 / ₩₩ 5~10만 / ₩₩₩ 10~18만 / ₩₩₩₩ 18만+)
              (confidence: "estimated")
          (c) Google Places price_level 보조 지표

[Layer 3] 확정 — 링크아웃
          계획서에 예약 페이지 링크 + "가격 확인 필요" 배지
          예산 정산표에 오차 범위 ±20% 병기
```

### 5.2 자체 시세 테이블 구축

```json
{
  "packId": "kr-gangneung",
  "priceBands": [
    { "area": "경포", "type": "hotel", "season": "peak_summer",
      "weekday": { "min": 120000, "max": 180000 },
      "weekend": { "min": 180000, "max": 280000 },
      "sampleSize": 42, "updatedAt": "2026-07-01" },
    { "area": "강릉역", "type": "guesthouse", "season": "normal",
      "weekday": { "min": 45000, "max": 70000 }, "…": "…" }
  ]
}
```

수집 방법: 분기별 수동 샘플링 + Google Places `price_level` 분포 + 사용자 피드백(여행 후 회고 설문에서 "실제 지불액" 수집). **회고 설문의 실지불액이 가장 값진 데이터**가 되므로 Phase 2에서 반드시 수집한다.

### 5.3 표시 원칙

| 상황 | 표시 |
| --- | --- |
| 실시간 확보 | `₩142,000/박` + `실시간` 배지 |
| 추정 | `₩₩₩ (약 12~18만/박)` + `추정 · 예약 시 확인 필요` 배지 |
| 불명 | 가격 없이 후보만 노출 + `가격 확인 필요` |

심판은 추정 후보와 실시간 후보를 비교할 때 **추정치의 상단 값**을 사용한다. 낙관적으로 잡아 예산이 터지는 것보다, 보수적으로 잡아 여유가 남는 편이 낫다.

## 8. 방 배정 서브문제

그룹 숙소에서 실제로 가장 예민한 부분인데, 대부분의 여행 플래너가 다루지 않는다. **말하기 껄끄러운 것을 대신 정리하는 것**이 이 서비스의 목적이므로 정면으로 다룬다.

### 8.1 설문에서 수집할 항목

민감 정보이므로 **본인이 명시적으로 입력한 것만** 사용하고, 추론하지 않는다.

| 항목 | 형식 | 다른 참여자에게 노출 |
| --- | --- | --- |
| 같은 방 희망 상대 | 참여자 다중선택 (선택) | ❌ 비공개, 배정 결과로만 반영 |
| 같은 방 곤란한 상대 | 참여자 다중선택 (선택) | ❌ 절대 비공개 |
| 1인실 희망 여부 | 예 / 아니오 / 추가비용 부담 가능하면 예 | 비용 발생 시에만 노출 |
| 코골이 자각 | 예 / 아니오 / 모름 | ❌ 배정에만 사용 |
| 수면 예민도 | 1~7 슬라이더 | ❌ |
| 방 배정 무관심 | 체크박스 | — |

> **"같은 방 곤란한 상대"는 어떤 경우에도 회의록·계획서에 드러나면 안 된다.** 배정 결과만 보여주고 이유를 밝히지 않는다. 이것이 드러나면 서비스가 인간관계를 파괴한다. 시스템 프롬프트에 명시적 금지 조항으로 넣는다.

### 8.2 배정 알고리즘

```
입력: 인원 N, 객실 구성 options[], roomingPreferences[]

[1] 하드 제약 필터
    · 곤란한 상대 쌍은 같은 방 배정 금지 (절대)
    · 1인실 필수 요청자는 별도 방 확보 (비용은 본인 부담 or 그룹 분담 — R6에서 결정)

[2] 가능한 배정 조합 열거 (N ≤ 8 이므로 완전 탐색 가능)

[3] 배정 점수
    Score = Σ 희망 상대와 동실 (+2)
          − Σ 코골이 자각자와 수면 예민도 6+ 인 사람 동실 (−3)
          − Σ 인원 불균형 (한 방만 4인, 나머지 2인) (−1)
          + 방 개수 최소화 보너스 (비용 절감)

[4] 최고 점수 배정안 채택
    동점 시 비용이 낮은 객실 구성 우선

[5] 미충족 선호 기록
    "예린님의 1인실 희망은 예산 제약으로 반영되지 못했습니다" 형태로 소수의견에 남김
```

### 8.3 배정이 후보 선택에 미치는 영향

객실 구성이 좋은 숙소는 배정 점수가 높아진다. 이것을 스코어링에 반영한다.

```
Sat(i, c) 의 comfortFit 항목에 배정 결과를 반영:
  · 희망 상대와 같은 방  → +0.15
  · 코골이 리스크 방     → −0.20
  · 1인실 확보           → +0.25 (요청자에 한해)
```

6인이 **한 채(아파트먼트)** 를 쓰는 경우가 특히 갈린다. `social` 슬라이더가 높은 사람에게는 큰 가점(다같이 논다), 수면 예민도가 높은 사람에게는 큰 감점(방 분리가 안 되면)이다. 심판은 반드시 `get_hotel_details`로 **침실 분리 여부**를 확인해야 한다.

```

        │
        ▼
[1] AREA SELECTION                              (LLM + 도구)

        │
        ▼
[2] CONSTRAINT COMPILE                          (결정론)
    maxPricePerPersonPerNight = budgetAllocated / nights

[4] SCREENING                                   (결정론)

        │
        ▼
[5] ROOM ALLOCATION                             (결정론)

        │
        ▼
[6] BRIEFING                                    (LLM)
    후보 카드 게시 — 가격·위치실측·객실구성·배정안·실격사유
        │
        ▼
[7] DEBATE                                      (오케스트레이터)

        │
        ▼

[11] HANDOFF
```

## 10. 하드 제약 매핑과 실격 규칙

| 설문 하드 제약 | 컴파일 | 실격 |
| --- | --- | --- |
| `dormitory` 불가 | `excludeTypes: ["dormitory"]` | 도미토리 실격 |
| 흡연실 불가 | `requiredAmenities: ["no_smoking"]` | 금연 불가 시설 실격 |
| 남녀 혼숙 불가 | 배정 알고리즘 제약 | 배정 불가능한 객실 구성 실격 |
| 휠체어 / 유아차 | `requiredAmenities: ["wheelchair"]` or `["elevator"]` | 미충족 실격 |
| 계단 불가 | `stepFree` 필수 | 엘리베이터 없는 시설 실격 |
| 예산 상한 | `maxPricePerPersonPerNight` | `effectiveLodgingCost` 초과 실격 |
| 주차 필수 (제주·강릉 자차) | `requiredAmenities: ["parking"]` | 미충족 실격 |
| 종교(기도 공간·할랄 조식) | 어메니티 확인 | 대안 제시 후 감점 |
| 반려동물 동반 | 어메니티 확인 | 미충족 실격 |

### 10.1 예산 상한의 처리

항공과 달리 숙소는 **분할 가능**하다. 따라서 최저 예산자 상한을 넘는 후보를 즉시 실격시키기 전에 대안을 검토한다.

```
if effectiveCost > min(personalBudgetForStay):
    1. 더 저렴한 객실 구성이 있는가? (트윈 3개 → 트리플 2개)
    2. 분할 숙박으로 평균을 낮출 수 있는가? (비싼 숙소 1박 + 저렴한 숙소 2박)
    3. 차액을 여유 있는 참여자가 분담할 의사가 있는가?
       → 이것은 심판이 결정하지 않는다. 절충안으로 제시하고
         에이전트들의 반응을 본 뒤, Chief에 판단을 넘긴다.
    4. 모두 불가하면 실격 + Chief 예산 경보
```

3번은 민감하다. **심판이 임의로 "부자가 더 내라"고 정하면 안 된다.** 제안만 하고, 강도 프로파일에서 거부 반응이 나오면 즉시 철회한다.

## 11. 스코어링 모델

### 11.1 개인 만족도

```
AccommodationCategorySat(i, c)
= Σ(detailImportance × fulfillment) / Σ(detailImportance)
```

숙소 중요도와 가격·위치·쾌적성·편의시설·취소 정책 같은 세부 중요도는 설문의 `5·3·1`을 사용한다. 기존 소비 성향 슬라이더 기반 동적 가중치는 분야 중요도와 중복되므로 제거한다.

| 항목 | 계산 |
| --- | --- |
| 가격 | 개인 예산 상한을 먼저 하드 게이트로 검사하고, 동급 후보는 `CostTravelComparator`에서 비교 |
| `locationFit` | `measure_location` 결과 × `mobilityPolicy.stationProximityWeight`. 택시 정책이면 역 거리 비중 하락, 활동 중심점 거리 비중 상승 |
| `comfortFit` | 방 배정 결과(8.3) + 침실 분리 + 욕실 형태. 세부 취향과 수면·접근성 제약으로 판정 |
| `qualityFit` | 평점 × log(리뷰 수) 정규화 + sentiment 점수 |
| `amenityFit` | 개인 카드 점수와 매칭 (온천 선호 9점인 사람에게 온천 보유는 큰 가점) |
| `cancelPolicyFit` | 무료 취소 가능 기간과 명시적 세부 취향으로 판정 |

모든 숙소 세부 취향의 반영도까지 동급일 때만 1~7 계획성·사교 등 관련 스타일 축의 `StyleFitBp`를 비교한다. 스타일은 숙소 만족도에 더하거나 `5·3·1`과 곱하지 않는다.

### 11.2 추가 규칙

```
[R-STAY-1] 료칸·펜션 등 식사 포함 시설은 effectiveLodgingCost 로 비교한다.
           식사 가치를 차감하지 않으면 구조적으로 불리해진다.
           동시에 R4 식사 예산에서 해당 끼니를 차감하도록 Chief에 통보한다.

[R-STAY-2] 야간 소음이 높은 지역(난바·스스키노·서면 등)의 숙소는
           수면 예민도 6+ 참여자의 comfortFit 에 −0.15.
           "번화가 한복판"은 누군가에겐 장점이고 누군가에겐 재앙이다.

[R-STAY-3] 도착 시각이 늦으면(21:00 이후) 늦은 체크인 가능 여부를 확인한다.
           확인 못 하면 uncertainties 에 기록한다.
           료칸·게스트하우스는 체크인 마감이 이른 경우가 많다.

[R-STAY-4] 성수기(Pack.peakSeasons) 날짜면 "빠른 예약 필요" 경고와
           예약 마감 권장일(체크인 45일 전)을 판결문에 명시한다.

[R-STAY-5] 분할 숙박은 이동 부담(짐 이동 1회 = 만족도 −0.3 상당)을
           반드시 비용에 반영해 비교한다. 싸다고 무조건 좋은 게 아니다.
```

## 12. 주장 강도 추정과 중재 로직

프레임워크는 `flight-referee-implementation.md` 11장과 동일. 여기서는 **숙소 라운드 고유의 신호와 함정**을 정의한다.

### 12.1 숙소 라운드의 강도 신호

| 신호 | 숙소에서의 구체적 발현 |
| --- | --- |
| S1 단정 | "도미토리는 절대 안 돼요" / "숙소는 잠만 자면 되잖아요" |
| S2 근거 | "지난번 여행에서 잠을 못 자서 다음 날 다 망쳤어요" |
| S3 반복 | 여러 턴에 걸쳐 위치 or 가격 반복 강조 |
| S4 양보 거부 | 분할 숙박 제안에도 "그래도 이동이 부담돼요" |
| S5 하드 제약 연계 | 등록된 절대조건(도미토리 불가 등) 근거 → 실격 사유로 승격 |
| S6 개인 비용 | "1박 8만원이면 3박에 24만원이에요" — 총액 환산은 강도 높음 |
| **S7 프라이버시 우려** | 방 배정 관련 발화. **강도가 낮게 표현되어도 실제 강도는 높다** |

### 12.2 숙소 라운드 고유의 함정 세 가지

**함정 1 — "잠만 자면 된다"의 비대칭**

숙소 분야 중요도가 낮고 가격 절약 세부 취향이 높은 사람의 "숙소는 잠만 자면 된다"는 주장은 강하게 표현되지만, 실제로는 **가격 선호**일 뿐이다. 반면 수면 예민도가 높은 사람의 "조용한 곳이 좋겠어요"는 약하게 표현되지만 **실질적 제약**이다.

```
→ 심판은 표현 강도가 아니라 설문 데이터로 검증한다.
  수면 예민도 6+ 인 사람의 소음 우려는 personaSupport 1.0
  숙소 분야 1점·가격 절약 세부 5점인 사람의 가격 주장도 personaSupport 1.0
  두 주장 모두 인정하되, 절충(조용한 지역의 저렴한 숙소)을 탐색한다.
```

**함정 2 — 방 배정 발화의 과소 표현**

"저는 아무 방이나 괜찮아요"라고 말하는 사람이 실제로는 1인실을 원하는 경우가 흔하다. 껄끄러워서 말을 못 한 것이다.

```
→ 심판은 방 배정에 관해서는 발화 강도를 무시하고
  설문의 roomingPreferences 를 절대 기준으로 삼는다.
  발화로 뒤집지 않는다.

  "말로는 괜찮다고 하지만 설문에 1인실 희망이 있으므로 반영합니다" 라고
  회의록에 쓰지 않는다 — 그것 자체가 프라이버시 침해다.
  조용히 배정에만 반영한다.
```

**함정 3 — 위치 주장의 검증 가능성**

"거기 역에서 가까워요"는 사실 주장이므로 강도와 무관하게 검증 대상이다.

```
→ measure_location 으로 즉시 검증하고, 틀렸으면 정정한다.
  강도가 아무리 높아도 사실이 틀리면 그 주장은 무효다.
```

### 12.3 페르소나 정합성 검증 예시

| 발화 | 설문 데이터 | 처리 |
| --- | --- | --- |
| "온천 있는 데로 가요" | 온천 카드 9점 | 100% 인정 |
| "온천 있는 데로 가요" | 온천 카드 3점 | 25% 할인 + 지적 |
| "숙소에 돈 쓰기 아까워요" | 숙소 분야 1점·가격 절약 세부 5점 | 100% 인정 |
| "숙소에 돈 쓰기 아까워요" | 숙소 분야 5점·고급 숙소 세부 5점 | 모순으로 표시하고 확인된 프로필 기준으로 제한 |
| "조용한 곳이 좋아요" | 수면 예민도 7 | 100% 인정 (약하게 말해도 강도 상향) |
| "도미토리 안 돼요" | 하드 제약 등록됨 | 실격 사유로 승격 |
| "역에서 5분이래요" | 실측 14분 | 사실 오류 — 정정 |

**"조용한 곳이 좋아요"의 강도 상향**이 이 심판의 특징이다. 다른 라운드에서는 약한 표현을 낮은 강도로 읽지만, 숙소의 수면·프라이버시 관련 발화는 **설문 데이터가 뒷받침하면 표현이 약해도 강도를 0.7 이상으로 읽는다.** 껄끄러워서 약하게 말하는 영역이기 때문이다.

### 12.4 강도 활용 범위

| 용도 | 사용 |
| --- | --- |
| 최종 후보 선택 | ❌ Maximin |
| 쟁점 축 식별 (가격 vs 위치 vs 쾌적) | ✅ |
| 절충안 방향 (분할 숙박? 객실 구성 변경? 지역 변경?) | ✅ |
| 강도 0.8 이상 반대자의 `Sat ≥ 5.5` 제약 | ✅ |
| 방 배정 | ❌ **설문만 사용** |
| 동점 타이브레이크 | ✅ |

## 13. 절충안 생성 전략

숙소는 절충 공간이 가장 넓은 라운드다. 심판은 아래 순서로 시도한다.

| 우선순위 | 교착 | 절충 전략 | 예시 |
| --- | --- | --- | --- |
| 1 | 가격 vs 등급 | **객실 구성 변경** | "트윈 3개 대신 트리플 2개 — 1인 8천원 절감" |
| 2 | 위치 vs 가격 | **지역 한 정거장 이동** | "난바 대신 닛폰바시 — 도보 7분 더, 1인 1.2만원 저렴" |
| 3 | 취향 양극 | **분할 숙박** | "시티호텔 2박 + 료칸 1박" |
| 4 | 프라이버시 vs 비용 | **부분 1인실** | "1인실 희망자만 추가 부담, 나머지 트윈" |
| 5 | 온천·특수 니즈 | **숙소 밖에서 해결** | "료칸 대신 시내 온천 시설 2회 — 1인 1.5만원" |
| 6 | 예산 초과 | **박수 조정** | "3박 → 2박 + 마지막 날 이른 귀국편" (R1 재검토 필요) |
| 7 | 완전 교착 | **Chief 예산 이관 요청** | "식사에서 2만원 이관 시 양쪽 안 모두 가능" |

### 13.1 분할 숙박의 조건

분할 숙박은 강력한 절충이지만 비용이 있다. 다음을 모두 만족할 때만 제시한다.

```
1. 총 비용이 단일 숙소 대비 +10% 이내
2. 이동 1회당 소요 30분 이내 (짐 이동)
3. 이동일이 활동 밀도가 낮은 날 (R5에 제약 전달)
4. 최소 만족도가 단일 숙소 최선안보다 0.4 이상 개선
5. 체력 제약자가 짐 이동을 감당 가능
```

evaluate_split_stay 도구가 이 조건을 자동 검증한다. 조건 미충족이면 심판은 분할안을 제시하지 않는다.

```
【원칙 2】 "가깝다"는 말을 믿지 마세요.

【원칙 3】 식사 포함 시설은 실효 비용으로 비교하세요.

【원칙 4】 객실 구성과 방 배정을 반드시 확인하세요.

【원칙 5】 야간 소음을 고려하세요.
  번화가 한복판은 누군가에겐 장점이고 누군가에겐 재앙입니다.
  get_area_profile 의 야간 소음 수준을 확인하고,
  수면 예민도가 높은 참여자가 있으면 감점 요인으로 명시하세요.

【원칙 6】 성수기와 예약 마감을 경고하세요.

  판결문에 예약 권장 마감일(체크인 45일 전)을 명시하세요.

  확인했을 때 이미 늦습니다.

【원칙 7】 늦은 체크인을 확인하세요.
  도착이 21시 이후인데 체크인 마감이 이른 숙소면 여행 첫날이 무너집니다.
  료칸·게스트하우스는 특히 체크인 마감이 이릅니다.

## 주장 강도 추정 (중재의 핵심 기술)

참여자 발언에서 각 주장의 강도를 0.0~1.0으로 추정하세요.

강도가 높다는 신호:
  · 단정적 표현 ("절대", "무조건")
  · 구체적 근거 2개 이상, 특히 과거 경험 ("잠을 못 자서 다음 날을 망쳤어요")
  · 여러 턴에 걸쳐 반복
  · 절충안에도 조건 고수
  · 등록된 하드 제약을 근거로 듦
  · 총액으로 환산해 말함 ("1박 8만원이면 3박에 24만원이에요")

강도가 낮다는 신호:
  · "괜찮을 것 같아요", "다들 좋다면"
  · 근거 없는 선호
  · 한 번 말하고 그침

★ 숙소 라운드의 특별 규칙 — 약하게 말해도 강도를 높게 읽어야 하는 경우 ★
  수면, 소음, 프라이버시, 방 배정에 관한 발화는
  껄끄러워서 약하게 표현되는 경향이 있습니다.
  "조용한 데가 좋을 것 같아요" 라고 약하게 말했더라도,
  그 사람의 설문 수면 예민도가 6 이상이면 강도를 0.7 이상으로 읽으세요.
  이런 사람은 회의에서 자기를 대변하지 못합니다. 당신이 대신 읽어야 합니다.

★ 반드시 설문과 대조해 보정하세요 ★
  · 주장이 하드 제약과 일치 → 100% 인정 (그리고 실격 사유입니다)
  · 주장이 슬라이더·카드 점수와 일치 → 100% 인정
      예: 숙소 분야 1점·가격 절약 세부 5점인 사람의 "숙소에 돈 쓰기 아까워요" → 100%
      예: 온천 카드 9점인 사람의 "료칸 가고 싶어요" → 100%
  · 설문에 근거 없음 → 50% 할인
  · 설문과 모순 → 25% 할인 + 회의록에 정중히 지적
      예: "민재님은 설문에서 온천을 3점으로 매기셨습니다.
           료칸 선호는 강도를 낮춰 반영하겠습니다."

  단, 방 배정 관련 정보는 이 지적의 대상이 아닙니다 (위 금지 조항 참조).

★ 사실이 틀린 주장은 강도와 무관하게 정정하세요 ★
  "역에서 5분"처럼 검증 가능한 주장은 measure_location 으로 확인하세요.

★ 강도를 최종 선택에 직접 쓰지 마세요 ★
  최종 후보는 언제나 "가장 불만족한 사람의 만족도가 가장 높은 안"입니다.
  강도는 다음에만 사용합니다:
    · 진짜 쟁점 식별 (가격인가, 위치인가, 쾌적함인가)
    · 절충안 방향 결정
    · 강도 0.8 이상 반대자의 만족도 하한(5.5)을 제약으로 추가
    · 동률일 때의 타이브레이크
  강도로 승자를 정하면, 이 서비스가 없애려던
  "목소리 큰 사람이 이기는 문제"를 그대로 재현하게 됩니다.

★ 강도 상한 ★
  한 사람이 한 라운드에서 강도 0.8 이상을 행사할 수 있는 것은 1회뿐입니다.
```

| 실시간 예약 | Amadeus Hotel Booking / Rakuten 예약 연동. 결제·PCI 요건 별도 |
| 가격 추적 | 확정 후 예약까지 가격 모니터링, 하락 시 알림 |
| 리뷰 요약 | Places 리뷰를 LLM으로 요약해 "그룹 여행 적합도" 추출 (소음·방음 언급 탐지) |
| 접근성 강화 | 배리어프리 상세 정보 DB, 휠체어 이용자 전용 필터 |

## 마무리 — 이 심판의 실패 조건

1. **위치를 실측하지 않으면 실패한다.** "역에서 가깝다"는 표기와 실제는 자주 다르고, 그 차이는 여행 내내 누적된다.
2. **식사 포함을 무시하면 실패한다.** 료칸·펜션을 순수 숙박비로 비교하면 구조적으로 배제된다. 실효 비용이 기준이다.
3. **방 배정 정보를 노출하면 실패한다.** 이것은 품질 문제가 아니라 **서비스 존속 문제**다. 누가 누구와 같은 방을 피하고 싶어했는지가 드러나는 순간, 이 서비스는 관계를 조율하는 도구가 아니라 파괴하는 도구가 된다.

## 20. v1.1 실행 보강 — 동시 재고·안전 게이트·분할 숙박 의존성

이 장은 `travel-mediation-plan.md` 19장의 Planning Graph·Booking Readiness·fail-closed 계약을 숙소 심판에 적용한다. 특히 기존 15장 예시의 H-05는 6인 동시 재고와 갑각류 대응이 미확인인 동안 winner가 아니다. 해당 예시는 두 조건을 확인하기 전에는 `PROVISIONAL/BLOCKED` 후보로 해석한다.

## 20.1 원자적 객실 조합 검증

시설의 총 수용 인원 표기와 선택한 객실 조합의 동시 재고는 다르다. 최종 후보는 다음을 하나의 snapshot에서 확인한다.

```text
checkIn/checkOut, 객실 타입별 수량, 각 객실 최대 인원, 침대 유형,
욕실 수·공용 여부, 총 객실가, 세금·리조트피·청소비·서비스료,
조식/석식 포함 범위, 취소·변경 규정, 체크인/아웃·짐 보관,
재고 조회 시각과 만료 시각
```

`groupInventoryVerified`, `roomCombinationVerified`, `allInPriceVerified`가 모두 true가 아니면 해당 후보는 `winner`, `VERIFIED`, `BOOKABLE`이 될 수 없다. 가격이 추정인 한국 Pack은 후보 탐색은 가능하지만 `BOOKABLE`로 승격하지 않으며, 보수적 상단값으로 Budget에 전달한다.

## 20.2 안전·접근성·체크인 fail-closed

식사 포함 숙소는 식사 가치를 차감하기 전에 알레르기·식이 대응 가능 여부와 실제 제공 끼니를 확인한다. 확인 실패 시 식사 크레딧을 계산하지 않으며, 해당 식사를 안전한 식당으로 대체할 수 없는 경우 숙소 후보를 채택하지 않는다.

연령·아동 정책, 금연, 엘리베이터/무단차, 휠체어 접근성, 주차, 늦은 체크인, 짐 보관은 해당 Mandate의 hard constraint일 때 확인 실패 시 fail-closed다. `uncertainties`에 기록하는 것만으로 Chief C5/C7을 통과할 수 없다.

## 20.3 분할 숙박의 예약 Saga

분할 숙박은 가격·만족도뿐 아니라 두 숙소의 예약 순서와 실패 보상을 가진다.

```text
H-A 객실 조합 검증 → H-B 객실 조합 검증 → 이동일 짐 보관/이송 검증
→ 두 예약의 취소 조건 확인 → Schedule의 이동 시간창 검증 → BOOKABLE
```

한쪽만 예약 가능한 경우 다른 쪽을 조용히 대체하지 않는다. 연결된 Schedule, Dining, Transport, Budget 노드를 `STALE`로 바꾸고, 일자별 체크인/아웃·짐 이동·활동 밀도·취소 수수료를 포함해 재최적화한다. 분할안은 이동 부담을 수치화할 뿐 아니라, 체력 제약자의 짐 이동 대리·택시·보관 비용이 검증된 경우에만 제시한다.

## 20.4 민감 방 배정 데이터 경계

`roomingPreferences` 원문과 배정 탐색 중간 결과는 private enclave에서 처리한다. 공동 뷰·회의록·도구 로그·LLM 프롬프트에는 다음만 노출 가능하다.

```text
객실 구성 충족 여부 / 최종 배정 결과 / 익명화된 편의성 영향 / 추가 비용
```

같은 방이 곤란한 상대, 코골이, 수면 예민도, 건강·성별·관계 정보는 식별 가능한 이유·점수·반대 의견·후보 실격 사유로 출력하지 않는다. 개인 뷰에도 본인 입력과 그 반영 여부만 보여준다. 방 배정은 발화 강도가 아니라 명시적 설문과 하드 제약만 사용한다.

## 20.5 한국 가격 밴드의 검증·갱신

한국 가격 밴드는 `sampleSize`, `samplePeriod`, `sourceMix`, `updatedAt`, `errorP50`, `errorP95`를 가진다. 실제 예약·사후 회고의 실지불액을 동의 기반으로 익명 집계해 분기별 backtest한다. P95 오차가 ±20%를 넘거나 표본이 임계치보다 적으면 Pack 등급을 낮추고, DateResolver·Budget은 더 넓은 보수적 구간을 사용한다.

## 20.6 전역 재최적화·테스트 보강

숙소 좌표, 체크인/아웃, 객실가, 식사 포함, 분할 숙박 여부가 바뀌면 Activity, Dining, Scheduler, Transport Pass, Budget은 `STALE`이다. 숙소 심판은 개별 숙소 만족도뿐 아니라 재계산된 전역 계획의 최소 만족도·총비용 범위·이동시간을 함께 비교한다.
