## 1. 무엇을 바꾸는가

사용자는 **에이전트들끼리의 대화(회의록)와 완성된 계획서를 본 뒤** 이의를 제기해 다시 토론시킬 수 있다. 기획서 8.6의 재개최를 정식 기능으로 승격하고, 다음을 새로 정의한다.

| 항목 | 기존 (기획서 8.6) | **이 문서** |
| --- | --- | --- |
| 제기 주체 | 방장 승인 필요 | **참여자 누구나.** 상한이 비용을 통제하므로 방장 승인을 기본 요구하지 않는다 |
| 횟수 | 방당 2회 무료 | **방 3회 + 1인 1회** (설정 가능, 3장) |
| 대상 지정 | 카테고리 | 카테고리 + **회의록 앵커**(판결·발언·후보 ID) |
| 근거 연결 | 없음 | 앵커된 주장을 심판이 **반드시 재검증** |
| 제약 추가 | "조건 추가하고 다시" | **늦은 하드 제약 등록**으로 정식화. 안전 항목은 fail-closed 재검증 |
| 사전 안내 | 없음 | 재실행 전 **영향 예측**(재계산 노드·시간·비용·예약 위험) 필수 노출 |

이의 제기는 실시간 개입이 **아니다.** 회의가 끝난 결과에 대한 사후 액션이므로 "설문 내고 방치" 원칙(기획서 3.1)을 깨지 않는다. 실시간 개입 채널은 여전히 영구 제외다(기획서 14.2).

## 2. 이의 제기 모델

### 2.1 유형

| kind | 의미 | 심판이 받는 것 |
| --- | --- | --- |
| `add_condition` | 조건을 추가해 다시 | 새 하드 제약 또는 예산 완화폭 + 이의 사유 |
| `replace_candidates` | 후보를 바꿔서 다시 | 배제 요청 후보 ID + 재조달 지시 |
| `redo` | 그냥 다시 | 이의 사유만. 다른 결과가 나올 수 있다는 안내 필요 |

### 2.2 회의록 앵커

이의는 회의록의 특정 지점을 지목할 수 있다. 앵커가 있으면 심판은 그 주장·판결·후보를 **팩트체크 단계에서 반드시 다시 검증**한다.

```json
{
  "verdictId": "v_r2",
  "claimIds": ["clm_104"],
  "candidateIds": ["H-03"],
  "messageSeqs": [12, 13]
}
```

앵커가 없는 이의는 `redo`와 동일하게 취급된다. **"어디가 잘못됐는지 지목하면 그 지점을 다시 본다"** 는 것이 이 기능의 핵심이며, Negotiation Causality Ledger(기획서 19.5)와 직접 연결된다.

### 2.3 이의 사유는 그대로 인용된다

사용자가 쓴 `reason`(300자 이내)은 요약·재작성 없이 재심 지시문과 회의록에 인용된다. 사용자는 회의에 참석하지 못했으므로, 이의 문장이 그가 남긴 유일한 발언이다.

## 3. 횟수 상한

```
방 전체 누적: 3회   (OBJECTION_CAP_PER_ROOM = 3)
1인 누적:     1회   (OBJECTION_CAP_PER_USER = 1)
실제 여유 = min(방 잔여, 1인 잔여)
```

두 상한을 함께 두는 이유는 **한 사람이 방 상한을 독점하지 못하게** 하기 위해서다. 목소리 큰 사람이 결과를 지배하는 것을 막는 것이 이 서비스의 정체성이고(기획서 8.3), 이의 제기에도 같은 원칙을 적용한다. 6명 방이면 최대 3명이 각자 1회씩 이의를 낼 수 있다.

거부·만료된 이의는 상한 계산에 넣지 않는다. 접수된(`accepted` 이상) 이의만 소모로 계산한다.

> **재검토 필요**: "1~3번"의 해석을 방 3회 + 1인 1회로 잡았다. 1인당 3회를 허용하려면 `OBJECTION_CAP_PER_USER=3`으로 올리면 되지만, 6인 방이면 최대 18회 재실행이 되어 원가 상한($0.6/방)을 크게 넘는다. 상한 변경 시 11장의 비용 계산을 함께 갱신할 것.

## 4. 심사 규칙

접수 시 아래 순서로 검사하고, 걸리면 사유를 그대로 사용자에게 노출한다.

| # | 거부 사유 | 조건 |
| --- | --- | --- |
| 1 | `room_not_completed` | 방 상태가 `COMPLETED`가 아니다. 회의 중에는 이의를 낼 수 없다 |
| 2 | `not_a_member` | 방 참여자가 아니다 |
| 3 | `unknown_target` | 지목한 라운드가 이 방에서 실행되지 않았다 (예: 국내 Pack의 항공 라운드) |
| 4 | `user_cap_exhausted` | 1인 상한 소진 |
| 5 | `room_cap_exhausted` | 방 상한 소진 |
| 6 | `duplicate_target` | 같은 사용자가 같은 라운드에 이미 이의를 냈다 |

구현: `packages/core/src/objection.ts`의 `screenObjection`. 전부 결정론이며 LLM을 쓰지 않는다.

## 5. 영향 산출과 재실행 범위

이의는 처음부터 다시 돌리지 않는다. 지목된 라운드의 **Planning Graph 노드와 그 하위 노드만** `STALE`로 만들고 해당 라운드만 재실행한다.

```
targetCategory → 산출 노드 → computeStaleNodes(노드) → roundsForNodes(STALE) → 재실행 라운드
```

숙소(R2)에 이의를 제기한 실측 결과:

```text
STALE 노드   accommodation · activity · dining · schedule · budget
             transit_pass · booking_readiness · validation · document
재실행 라운드 r_1b · r_2 · r_3 · r_4 · r_5 · r_6
예상 소요     900초 · 예상 비용 $0.3
```

`r_1b`(교통)가 포함되는 것은 의도된 동작이다. 숙소 좌표가 바뀌면 교통패스 손익과 이동시간 행렬이 함께 무효가 된다(교통 19.1). 이의 하나가 여섯 라운드를 되돌리므로, 이 숫자를 사용자에게 **먼저 보여주는 것**이 중요하다.

소요·비용 추정치는 현재 라운드당 150초·$0.05의 거친 상수다. 실측 p50/p95로 교체할 자리다(agent-architecture 12.2).

## 6. 늦은 하드 제약 등록

설문에서 놓친 제약이 영구히 반영되지 않는 것은 이 서비스의 구조적 리스크다(기획서 R3). 이의의 `add_condition`이 그 **유일한 회복 경로**다.

```json
{ "tag": "숙소 이동 불가", "kind": "forbidden", "safety": false }
{ "tag": "갑각류", "kind": "allergy", "safety": true }
```

| `safety` | 처리 |
| --- | --- |
| `false` | 일반 하드 제약으로 승격. 해당 라운드부터 실격 필터에 반영 |
| `true` | **fail-closed 재검증 대상.** 관련 후보는 대응 확인 전까지 `winner`/`VERIFIED`/`BOOKABLE`이 될 수 없다 |

안전 제약(알레르기·접근성)이 뒤늦게 등록되면 이미 확정된 식당·숙소가 무효가 될 수 있다. 이때 조용히 차선책으로 바꾸지 않고, 영향 노드를 `BLOCKED`로 표시하고 사용자에게 알린다(기획서 19.6).

## 7. 승인이 필요한 경우

아래에 해당하면 이의는 `needs_approval`로 남고 **자동 실행되지 않는다.**

| 사유 | 이유 |
| --- | --- |
| `booked_node_change` | 예약 완료(`BOOKED`) 노드가 흔들린다. 취소 수수료·재예약 위험을 먼저 보여야 한다 |
| `date_change` | R0 대상 이의. 날짜는 모든 하위 노드를 흔들고 참석 가능 여부까지 바꾼다 |
| `exclude_attendee` | 인적 관계에 영향을 준다 |
| `budget_over_10_percent` | 1인 예산 기준선의 10%를 넘는 완화 요청 |

승인 주체는 방장이다. 승인 대기는 기획서 19.2의 `approval_required` 계약과 동일하게 **비동기 승인 요청**으로 처리한다.

## 8. 실행 흐름

```
[결과 화면]  회의록·계획서 열람
     │
     ▼
[preview]    POST /objections/preview
             → 재계산 노드·라운드·시간·비용·예약 위험·남은 횟수 표시
     │  사용자가 확인
     ▼
[submit]     POST /objections
             → screenObjection 통과 → 영향 산출 → accepted 또는 needs_approval
     │
     ├─ needs_approval → 방장 승인 대기 → 승인 시 accepted
     ▼
[queue]      rerun_from_objection 잡 등록 (jobId = rerun:{objectionId} — 멱등)
     │
     ▼
[worker]     STALE 노드 재계산 → 대상 라운드만 재실행
             심판은 앵커된 주장을 반드시 재검증하고, 이의 사유를 지시문으로 받는다
     │
     ▼
[applied]    전후 diff(최소 만족도·예산·동선) 기록 → 알림
             반영되지 못했으면 unresolvedReason을 반드시 남긴다
```

방 상태 전이: `COMPLETED → OBJECTION_RAISED → QUEUED → RUNNING → COMPLETED`

## 9. API 계약

| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| GET | `/api/rooms/:roomId/objections` | 상한·사용량·잔여 횟수와 접수 이력 |

## 10. UX 계약

- 결과 화면의 각 결정 카드에 **[이 결정 다시 논의하기]** 를 둔다. 남은 횟수를 함께 표시한다.
- 회의록에서 특정 발언·판결을 선택해 이의를 걸 수 있게 한다(앵커 생성).
- preview 결과를 건너뛰고 제출할 수 없다. **무엇이 다시 계산되는지 모른 채 이의를 내면 도박이 된다.**
- 재실행 후에는 전후 비교를 보여준다: 최소 만족도, 1인 예산, 총 이동시간, 바뀐 항목.
- 이의가 반영되지 않았을 때도 결과를 보여주고 사유를 밝힌다. **"다시 돌렸지만 같은 결론"** 도 정당한 결과다.
- 이의 사유와 재심 사실은 회의록에 남는다. 누가 냈는지는 방 공동 뷰에 노출하지 않는다(익명 처리).

## 11. 비용·남용 통제

| 장치 | 내용 |
| --- | --- |
| 이중 상한 | 방 3회 + 1인 1회 |
| 중복 차단 | 같은 사용자·같은 라운드 재제기 금지 |
| 부분 재실행 | 전체 run이 아니라 STALE 라운드만 |
| 멱등 잡 ID | `rerun:{objectionId}` — 중복 요청도 1회만 실행 |
| 원가 추적 | `llm_usage`에 재실행분을 구분 기록. 방당 상한($0.6) 소진 시 축약 모드 |
| 만료 | 결과 발행 후 N일이 지나면 이의 접수를 닫는다 (미결정 2번) |

숙소 이의 1회가 6개 라운드 재실행($0.3 추정)이므로, 방 3회면 최악의 경우 최초 실행의 1.5배 원가가 추가된다. 상한을 올리기 전에 실측이 필요하다.

## 12. 테스트 케이스

| # | 시나리오 | 기대 동작 |
| --- | --- | --- |
| O1 | 회의 진행 중 이의 제기 | 409 `room_not_completed` |
| O2 | 같은 사용자가 2회 제기 | 409 `user_cap_exhausted` |
| O3 | 서로 다른 3명이 각 1회 제기 | 모두 접수, 4번째는 `room_cap_exhausted` |
| O4 | 같은 사용자가 같은 라운드에 재제기 | 409 `duplicate_target` |
| O5 | 국내 Pack에서 항공 라운드(r_1a) 지목 | 409 `unknown_target` |
| O6 | 숙소 이의 preview | STALE 9개 노드, 재실행 6개 라운드, 비용·시간 표시 |
| O7 | 예약 완료 노드에 영향 | `needs_approval` + `cancellationRisk: high` |
| O8 | R0(날짜) 지목 | `needs_approval` + `date_change` |
| O9 | 예산 기준선의 15% 완화 요청 | `needs_approval` + `budget_over_10_percent` |
| O10 | 알레르기 늦은 등록 | `failClosedRecheck: true`, 관련 후보 BOOKABLE 금지 |
| O11 | 재실행 결과가 동일 후보 | `outcome.changed: false` + 사유 노출 |
| O12 | 같은 objectionId로 잡 2회 등록 | 멱등 — 1회만 실행 |

## 13. 미결정 사항

| # | 항목 | 결정 시점 |
| --- | --- | --- |
| 1 | 1인 상한을 1회로 둘지 3회로 열지 (원가 실측 필요) | Phase 0 실측 후 |
| 2 | 이의 접수 만료 기간 (결과 발행 후 며칠) | 베타 운영 시 |
| 3 | 유료 플랜에서 상한을 늘릴지 (기획서 17.2 프리미엄 혜택) | Phase 2 |
| 4 | 앵커된 주장 재검증을 심판 프롬프트에 어떻게 주입할지 | 심판 프롬프트 구현 시 |
| 5 | 이의 제기자를 회의록에 익명으로 남길지 실명으로 남길지 | 프라이버시 정책 확정 시 |
