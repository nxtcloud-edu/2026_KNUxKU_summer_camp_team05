## 1. 문제 정의와 서비스 컨셉

### 1.1 문제

지인 단위(3~8명) 여행에서 계획 수립이 실패하는 이유는 정보 부족이 아니라 **의사결정 비용**이다.

| 문제 | 구체적 양상 |
| --- | --- |
| 총무 과부하 | 한 명이 검색·조율·정산을 전담하다 지쳐 계획이 지연되거나 무산 |
| 침묵하는 불만 | "난 아무거나 괜찮아"라고 말한 사람이 여행지에서 가장 불만족 |
| 갈등 회피 비용 | 예산·체력·종교·식이 제약처럼 말 꺼내기 껄끄러운 조건이 공유되지 않음 |
| 결정 마비 | 단톡방에서 링크만 100개 쌓이고 결론이 안 남 |
| 불공정 누적 | 목소리 큰 사람 취향이 전 일정을 지배, 나머지는 계속 양보 |
| **동시 참여 불가** | 6명이 같은 시간에 모여 논의할 수 있는 시간대가 존재하지 않음 |

마지막 항목이 v1.1의 핵심 전제다. **실시간 합의를 요구하는 순간 서비스는 실패한다.** 각자 편한 시간에 7분 설문만 하고 잊어버리면, 나중에 결과가 도착해 있어야 한다.

### 1.2 컨셉

**"설문만 내고 잊어버려라. 당신의 대리인이 대신 싸워둔다."**

1. 방장이 **목적지가 확정된 방**을 만든다 (예: "오사카 3박 4일 방")
2. 참여자는 각자 편한 시간에 설문을 작성하고 페르소나 카드를 확인한다
3. 전원 완료 시 백그라운드에서 **7라운드 회의가 자동 실행**된다 (실행 시간 무관)
4. 완료 알림이 오면, 사용자는 **최종 계획서 + 회의록 전문**을 확인한다

사용자가 회의 중에 할 일은 없다. 결과에 불만이 있으면 카테고리를 지정해 **재개최(rerun)** 를 요청한다.

### 1.3 핵심 가치

1. **투입 시간 7분** — 참여자가 쓰는 시간은 설문 한 번뿐.
2. **관전 가능한 의사결정** — 결과만 주는 AI 플래너와 달리, "왜 이 숙소인가"가 대화 로그로 남는다.
3. **감정 없는 갈등 대행** — 사람 사이 마찰 없이 이해충돌이 표면화되고 해소된다.
4. **정량화된 공정성** — 누가 얼마나 양보했는지 수치로 추적되고 다음 라운드에 보정된다.
5. **환각 없는 그라운딩** — 에이전트는 심판이 API로 가져온 실제 후보 카드 안에서만 논쟁한다.

## 2. 핵심 차별점

| 구분 | 기존 AI 여행 플래너 | 본 서비스 |
| --- | --- | --- |
| 입력 | 한 사람의 프롬프트 | N명의 구조화된 페르소나 |
| 참여 방식 | 실시간 대화형 | **완전 비동기 · 설문 후 방치** |
| 일정 조율 | 사용자가 날짜를 직접 지정 | **설문에서 수집해 자동 확정** (전원 가능 구간 + 항공료 최적) |
| 과정 | 블랙박스 | 회의록 전문 + 판결문 공개 |
| 근거 | LLM 내부 지식(환각 위험) | 심판이 호출한 실제 API 결과 |
| 갈등 | 무시하거나 평균화 | 명시적 충돌축 추출 → 협상 → 절충 |
| 공정성 | 없음 | 현재 Plan의 선호 손실도 기반 동점 보정 |
| 산출물 | 일정표 텍스트 | 일정표 + 예산 정산 + 반대의견 기록 + 플랜B |

> **결정적 설계 원칙**: 사용자가 중간에 개입할 수 없다면, 토론은 **연출이 아니라 진짜 탐색**이어야 한다. 사람이 고칠 기회가 없으므로 알고리즘과 심판이 그 책임을 전부 진다. 대화가 결과를 실제로 바꾸지 못하면 이 서비스는 "비싸고 느린 랜덤 추천기"가 된다.

## 3. 사용자 플로우 (비동기 모델)

```
[방장]                                    소요 30초
  1. 목적지 선택 (프리셋 카드: 강릉 / 오사카 / 교토 …)
  2. 초대 링크 발급 → 카카오톡 공유
     ※ 날짜·기간·예산을 정하지 않는다. 전부 설문에서 수집된다.
        │
        ▼
[참여자 × N]                              소요 7분 · 각자 편한 시간
  3. 링크 진입 → 소셜 로그인
  4. 설문 응답
     ⓪ 가용 일정 — 갈 수 있는 날짜(캘린더 다중선택) + 방장 제안 여행 기간 확인  ★신규
     ① 하드 제약 (예산 상한, 식이/알레르기, 신념, 체력, 절대 불가)
     ② 취향 슬라이더 12
     ③ 목적지 특화 카드 20장 선호도 1~10
     ④ 목적급 콘텐츠 0~2개 + 절대 피하고 싶은 것
  5. 페르소나 카드 확인 및 수정  ★ 사용자의 마지막 통제 지점
  6. 완료 → 앱을 닫는다. 이후 할 일 없음.
        │
        ▼
[시스템 — 백그라운드]                      소요 5~20분 (사용자 대기 불필요)
  7. 전원 제출·필수조건 검증 완료 → SurveySnapshot 잠금 후 트리거
     └ 미완료자가 있으면 마감이나 방장 시작 요청으로 우회하지 않고 COLLECTING 유지
  8. 하드 제약 통합 및 충돌 검사 (Chief)
  9. DateResolver — 전원 가능한 연속 구간 산출 → 후보 1~3개  ★신규
 10. R0(프레이밍) — 일정 확정 + 컨셉·페이스·예산 사용 우선순위
     └ 날짜 후보가 1개면 즉시 확정 공지, 2개 이상이면 짧게 토론 후 Chief 판결
 11. R1 → R6 순차 실행 (배치 LLM 호출)
     └ 확정된 날짜가 항공·숙소 심판의 조회 파라미터로 주입됨
 12. 동선 최적화 · 예산 정산 · 계획서 생성
 13. 자체 검증(Validation Pass) — 환각·모순·물리적 불가능 전수 점검
        │
        ▼
[알림]
 13. 카카오 알림톡 / 푸시: "오사카 여행 계획이 완성되었습니다"
        │
        ▼
[결과 확인]                                소요 5분
 14. 최종 계획서 (일정표 / 예약 링크 / 정산표 / 플랜B)
 15. 회의록 리플레이 — 라운드별 토론을 타이핑 연출로 재생
 16. 각자 만족도 표시 및 소수 의견 확인
 17. 불만 시 → [이 라운드 다시 열기] 요청 (방장 승인 → 재실행)
```

### 3.1 실시간 개입이 없어서 생기는 것들

개입 채널(지시·직접발언·거부권)을 제거하면 UX는 단순해지지만, 그 책임은 전부 시스템으로 이관된다.

**얻는 것**

| 항목 | 효과 |
| --- | --- |
| 참여 장벽 | 설문 7분이 전부. 일정 조율 불필요 |
| 지연시간 제약 소멸 | 90초 안에 끝낼 필요 없음 → **더 깊은 토론 가능** |
| 원가 | 배치 API(비동기 처리) 활용 가능 → LLM 비용 **40~50% 절감** |
| 인프라 | SSE 실시간 스트리밍 불필요 → 큐 기반 잡으로 단순화 |
| 재현성 | 실행이 결정적이므로 A/B 테스트·회귀 테스트 가능 |
| 회의록 품질 | 사용자 개입으로 흐름이 끊기지 않아 논리가 일관됨 |

**잃는 것과 보완 장치**

| 잃는 것 | 보완 |
| --- | --- |
| 거부권 (절대 반대 표명) | **설문의 "절대 불가" 항목을 하드 제약으로 승격.** 심판이 후보 단계에서 실격 처리. 즉, 거부권을 사후 행사에서 사전 등록으로 옮김 |
| 라운드 승인 투표 | **Chief Referee의 자동 재심 트리거** (8.5절). 최소 만족도가 임계치 미만이면 사람 개입 없이 해당 라운드를 자동 재개최 |
| 오해 정정 기회 | **페르소나 확인 단계를 필수 게이트로 격상.** 미확인 참여자가 있으면 회의를 시작하지 않음 |
| 실시간 몰입감 | **회의록 리플레이** — 저장된 로그를 타이핑 연출로 재생. 실시간 생성보다 오히려 연출 통제가 쉬움 |
| 결과 불만 해소 | **사후 재개최(Rerun)** — 카테고리 지정, 방당 2회 무료 |

### 3.2 트리거 조건

회의는 모든 활성 참가자의 설문 제출, 페르소나 확인, 필수조건 검증이 완료된 뒤에만 시작한다. 방장의 `지금 시작`이나 마감기한 도달은 이 게이트를 우회할 수 없다.

1. 전원 설문 제출 + 페르소나 확인 + 필수조건 검증 완료
2. 불변 `SurveySnapshot` 생성 및 설문 잠금
3. 방장이 시작하거나 자동 실행 예약 시각 도달

단, **DateResolver가 유효한 날짜 후보를 1개 이상 찾지 못하면 회의를 시작하지 않는다.** 대신 방장에게 조정 옵션을 제시한다 (3.3절).

미응답자는 기본 페르소나로 대체하거나 자동 제외하지 않는다. 방장은 작성 요청, 마감 연장, 이번 계획의 활성 참가자에서 명시적 제외 중 하나를 선택한다. 제외된 참가자의 제약과 취향은 전체 계산에서 제거하고 결정은 감사 로그에 남긴다. 이 선택 전에는 후보 탐색과 Agent 실행을 시작하지 않는다.

### 3.3 날짜 확정 실패 시 (전원 가능한 구간이 없을 때)

이 케이스는 흔하지만 날짜는 선호가 아니라 참여 가능성을 결정하는 하드 제약이다. 전원 가능 구간이 없으면 자동으로 일부 참석 일정을 만들지 않고 `DATE_BLOCKED` 상태를 유지한다.

```
[DATE_BLOCKED]
    "모든 활성 참가자가 가능한 연속 여행 구간이 없습니다."
      ○ 참가자들에게 가능 날짜 수정 요청
      ○ 전원 동의를 받아 여행 기간 축소
      ○ 특정 참가자를 이번 계획의 활성 인원에서 명시적으로 제외
      ○ 방의 검색 가능 날짜 범위 변경
        │
        ▼
    입력·동의·활성 인원 변경을 새 SurveySnapshot으로 잠금
        │
        ▼
    DateResolver 재실행
```

`N-1` 구간, 최다 참석 구간, 미응답자의 추정 날짜는 계산하거나 자동 선택하지 않는다. 방장도 기존 스냅샷의 불가능 날짜를 임의로 가능한 날짜로 변경할 수 없다.

## 5. 설문 설계 (Preference Intake)

설문 품질이 곧 에이전트 품질이다. 개입 채널이 없으므로 **설문이 유일한 입력**이다. 목표 소요 시간 **7분 이내**.

### 5.1 섹션 구성

**⓪ 가용 일정 (Availability) — v1.2 신설 · 가장 먼저 묻는다**

방장이 날짜를 정하지 않으므로 이 섹션이 일정의 유일한 입력원이다. 설문 첫 화면에 배치해 이탈 전에 확보한다.

| 문항 | 형식 | 비고 |
| --- | --- | --- |
| 갈 수 있는 날짜 | 캘린더 다중선택 (향후 6개월) | 기본값: 주말 전체 선택된 상태로 시작 → 입력 부담 감소 |
| 절대 안 되는 날짜 | 캘린더 다중선택 | 위와 별도. 시험·행사·출장 등 |
| 여행 기간 확인 | 방장이 제안한 정확한 N박 N+1일에 동의 / 재조정 요청 | 전원 동의 전 DateResolver 실행 금지 |
| 휴가 사용 가능 여부 | 주말만 / 금요일 연차 가능 / 평일도 가능 | 후보 구간 확대 여부 결정 |
| 항공 시간대 유연성 | 새벽 가능 / 오전 이후만 / 상관없음 | 항공권 심판이 재사용 |

> **UX 원칙**: "가능한 날"을 일일이 찍게 하면 이탈한다. 주말이 미리 선택된 상태에서 시작하고, "여기에 평일 휴가를 더할 수 있어요" 정도의 보조 액션만 둔다. 평균 입력 시간 목표 **40초**.

MVP에서는 참가자별 희망 박수와 `±1박 자동 유연성`을 받지 않는다. 방장이 정확한 기간을 제안하고 모든 활성 참가자가 확인하면 `DurationAgreement.AGREED`로 저장한다. 기간을 바꾸면 기존 동의와 스냅샷은 무효가 되며 전원 재확인 후 새 `SurveySnapshot`을 생성한다. Destination Pack의 `recommendedNights`는 방장에게 보여주는 참고 정보일 뿐 자동 결정값이 아니다.

**① 하드 제약 (Hard Constraints) — 협상 불가 · 사전 등록형 거부권**

개입 채널이 없어진 만큼 이 섹션의 비중을 v1.0보다 키운다. "이건 절대 안 된다"를 여기서 말하지 않으면 말할 기회가 영영 없다.

- 1인 총예산 상한 (슬라이더, 원화 / 항공 포함 여부 체크)
- 식이 제약: 비건 / 베지테리언 / 할랄 / 코셔 / **알레르기(다중 선택)** / 없음
- 종교·신념: 기도 시간 확보, 특정 요일 활동 제한, 음주 여부, 동물윤리(동물체험 거부)
- 신체 조건: 하루 도보 가능 거리, 계단·경사 제약, 휠체어·유모차 여부
- **절대 불가 항목 (태그 다중 선택 + 자유 입력)**
  - 프리셋 예시: 새벽 비행 불가 / 도미토리 불가 / 남녀 혼숙 불가 / 날것 불가 / 번지·놀이기구 불가 / 장시간 버스 불가 / 흡연실 불가
  - UI 문구: **"여기 적지 않으면 회의에서 반영되지 않습니다"** ← 명시적 경고

**② 소프트 취향 (Soft Preferences) — 협상 가능**

7점 슬라이더 11문항. 각 문항은 상충하는 양극단으로 설계한다. 슬라이더는 분야·세부 `5·3·1`과 곱하지 않고 일정 구성과 동급 후보 비교에만 사용한다.

| 축 | 좌 ← → 우 |
| --- | --- |
| 페이스 | 하루 1~2곳 여유 ← → 하루 5곳 이상 빡세게 |
| 계획성 | 즉흥·현장결정 ← → 분단위 확정 |
| 관심사 | 자연·풍경 ← → 도심·쇼핑 |
| 문화 | 역사·박물관 ← → 트렌디·핫플 |
| 식사 | 현지 로컬 도전 ← → 검증된 안전한 맛집 |
| 사교 | 다같이 항상 ← → 자유시간 필수 |
| 기상 | 새벽형 ← → 늦잠형 |
| 야간 | 술·나이트라이프 중요 ← → 저녁엔 휴식 |
| 이동 | 택시 써서 편하게 ← → 대중교통으로 아끼기 |
| 사진 | 인생샷 필수 ← → 사진 관심 없음 |
| 리스크 | 액티비티·모험 ← → 안전·무난 |

기존 소비 성향 축은 음식·숙소 분야 우선순위 `5·3·1`과 같은 질문을 반복하므로 MVP에서 제거한다. 후보·Plan의 스타일 태그는 Destination Pack 또는 검증 코드가 1~7로 부여한다. Agent가 값을 생성하지 않는다.

```text
StyleFitBp(i, candidate, axis)
= round(10000 × (1 - abs(userValue - candidateStyle) / 6))
```

미응답 축은 계산에서 제외한다. 모든 세부 취향 계층이 동급일 때 참가자별 최소 StyleFit을 먼저, 응답자 평균을 다음으로 비교하며 이후 선호 손실도·비용·동선 순으로 넘어간다. 안전·건강·접근성 하드 제약은 StyleFit보다 항상 우선한다.

**③ 목적지 특화 카드 선호도 (1~10)**

목적지가 확정되어 있으므로 **해당 Destination Pack의 전용 덱 20장**을 쓴다. 카드 1장 = 실사 이미지 + 한 줄 설명 + 슬라이더(1~10).

*`kr-gangneung` 덱 예시*
경포해변 / 안목 카페거리 / 서핑 강습 / 주문진 회센터 / 오죽헌·역사탐방 / 정동진 일출 / 바다뷰 숙소 / 대관령 양떼목장 / 초당순두부 / 강릉중앙시장 / 하슬라아트월드 / 바다 카약 / 경포호 자전거 / 감자옹심이 노포 / 안반데기 별보기 / 테라로사 / 강문해변 야경 / 캠핑·차박 / 스카이베이 인피니티풀 / 짬뽕순두부 웨이팅

*`jp-osaka` 덱 예시*
도톤보리 야경 / 유니버설 스튜디오 / 구로몬 시장 / 오사카성 / 신세카이·쿠시카츠 / 우메다 스카이빌딩 / 이자카야 하시고자케 / 스시 오마카세 / 덴덴타운(애니·전자) / 신사이바시 쇼핑 / 스파월드 온천 / 츠텐카쿠 / 나카노시마 미술관 / 다코야키 투어 / 한신백화점 식품관 / 교토 당일치기 / 고베 당일치기 / 오사카 아쿠아리움 / 아메무라 빈티지 / 야키니쿠 츠루하시

> 카드 점수는 **에이전트의 논거 재료**로 직접 쓰인다. "지훈님은 스파월드 9점, 신사이바시 쇼핑 2점"이 발화 근거가 된다. 목적지가 고정되어 있으므로 이 신호는 v1.0의 "국가 일반" 덱보다 훨씬 정밀하다.

**④ 목적급·제외 자유 서술 (각 100자)**

- "이번 여행에서 이것만은 꼭 하고 싶다" — `purposeItems` 최대 2개, 입력 순서가 1·2순위
- "이것만은 정말 피하고 싶다"

LLM이 태그로 정규화한 뒤 **반드시 본인에게 확인**받는다. 두 번째 문항에서 추출된 강한 부정 표현("절대", "죽어도")은 하드 제약 후보로 승격해 확인을 요청한다.

목적급 상한은 MVP에서 참가자당 2개다. 두 항목 모두 최종 확정 게이트이며 2순위를 Agent가 자동 포기하거나 일반 취향으로 강등할 수 없다. 순위는 검색·배치·대체안 제시 순서에만 사용한다. 동일한 정규화 대상과 핵심 속성을 가진 여러 참가자의 목적은 한 일정 슬롯으로 병합한다. 중복 제거 후 모두 배치할 수 없으면 Plan v0에 `OBJECTIVE_CAPACITY_CONFLICT`를 남기고 관련 사용자의 승인 전 최종 확정을 차단한다. 상한은 `maxPerParticipant` 정책값으로 분리해 향후 확장한다.

### 5.2 페르소나 카드 확인 — 필수 게이트

개입 채널이 없는 구조에서 **이 단계가 사용자의 유일하고 마지막인 통제 지점**이다. 따라서 건너뛸 수 없는 필수 게이트로 만든다.

```

  서지훈 — "온천 지상주의 실속파"
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  예산      1인 90만원 (항공 포함) · 상한 엄격
  페이스    느긋 (하루 2~3곳)
  🚫 절대조건  새벽 비행 불가 · 갑각류 알레르기
  최우선    스파월드 온천(9) · 이자카야(8) · 다코야키 투어(8)
  무관심    신사이바시 쇼핑(2) · 아쿠아리움(1)

        [ 이대로 보낼게요 ]   [ 수정할래요 ]
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

- 미확인 참여자가 1명이라도 있으면 **회의를 시작하지 않는다**
- 확인 후에는 라운드 시작 전까지만 수정 가능
- 확인 화면의 문구는 "당신이 회의에 참석하지 않는다"는 사실을 분명히 알려야 한다

## 6. 에이전트 아키텍처

### 6.1 에이전트 계층

```
┌─────────────────────────────────────────────────────────┐
│  Orchestrator (LLM 아님 · 결정론적 상태머신)              │
│  라운드 진행 / 발언 순서 / 종료 조건 / 예산 가드            │
└───────────────┬─────────────────────────────────────────┘
                │
    ┌───────────┼───────────────────────────┐
    ▼           ▼                           ▼
┌─────────┐ ┌──────────────────┐  ┌──────────────────────┐
│ 참여자   │ │ 카테고리 심판     │  │ 총괄 심판(Chief)     │
│ 에이전트 │ │ (라운드마다 교체) │  │ 전 라운드 일관성 감독 │
│  × N    │ │  + typed tool만   │  │  + 예산 총량 감시     │
└─────────┘ └──────────────────┘  │  + 자동 재심 트리거 ★ │
                    │             └──────────────────────┘
                    ▼
        ┌────────────────────────┐
        │ 결정론적 Data Gateway  │
        │ + Provider Connector   │
        │ (API 호출·정규화·근거)   │
        └────────────────────────┘
```

★ 사용자 승인 투표가 없어진 만큼, Chief Referee가 그 역할을 대신한다.

### 6.2 참여자 에이전트 (Persona Agent)

**역할**: 자기 주인의 이익을 최대화하되, 회의를 결렬시키지 않는다.

**입력 컨텍스트**
- 자기 페르소나 카드 (전체)
- 다른 참여자 페르소나 (**요약본만** — 하드 제약 + 상위 3개 선호. 전체를 주면 지나치게 협조적이 되어 토론이 죽는다)
- 현재 라운드 후보 카드 목록 (심판이 API로 조회한 실제 데이터)
- 직전 3턴 대화 + 이전 라운드 판결 요약
- 자신의 취향 반영·부분 반영·미반영 내역

**행동 정책 (Behavior Policy)**
- 발화는 **3문장 이내**. 회의록을 나중에 읽는 구조이므로 장문은 곧바로 이탈로 이어진다.
- 반드시 **후보 ID를 명시**해 지지/반대한다 (`H-02 지지`)
- 자기 페르소나에 없는 정보를 지어내지 않는다
- 하드 제약 위반 후보에는 반드시 반대한다
- 선호 손실도는 Proxy의 공격성이나 말투를 바꾸지 않고 동점 후보 보정에만 사용한다
- **주인이 개입할 수 없다는 사실을 안다** → 애매하면 물러서지 말고, 대신 조건부 수용(conditional)을 제시한다

**협상 스타일 파라미터** (설문에서 유도 or 자동 배정)

| 스타일 | 특징 |
| --- | --- |
| 주장형(Assertive) | 선호를 강하게 밀고 근거를 반복 |
| 조정형(Mediating) | 절충안을 먼저 제시 |
| 실속형(Economical) | 가성비·예산 논거 중심 |
| 관조형(Easygoing) | 대체로 동의하나 하드 제약엔 완강 |

스타일은 재미 요소가 아니라 **탐색 다양성 확보 장치**다. 전원이 조정형이면 첫 후보가 그대로 통과한다. 오케스트레이터는 그룹 내 스타일 분포가 한쪽으로 쏠리면 최소 1명을 주장형으로 강제 배정한다.

### 6.3 심판 에이전트 (Referee Agent)

카테고리마다 **다른 시스템 프롬프트 + 다른 API 도구 + 다른 판정 기준**을 가진다.

**공통 책무 (4단계)**

1. **후보 조달(Sourcing)** — Destination Pack의 제공자 우선순위에 따라 API 호출, 후보 5~8개 확보
2. **팩트체크(Grounding)** — 토론 중 나온 주장 검증 ("조식 포함 아닙니다", "도보 15분이 아니라 34분입니다")
3. **제약 심사(Screening)** — 하드 제약 위반 후보 실격 처리
4. **판결(Verdict)** — 스코어링 + 판결문 + 소수의견 기록

**심판의 권한 제한**
- 심판은 **후보를 발명하지 않는다.** 반드시 API 응답에 있는 항목만 제시
- 심판은 **하드 제약을 무시할 수 없다.** 오케스트레이터가 사전 필터링한다
- 심판의 판결은 **Chief의 자동 재심 조건에 걸리면 무효화**된다

### 6.4 총괄 심판 (Chief Referee) — 권한 강화

사용자 승인 투표가 사라졌으므로, 품질 게이트를 Chief가 전담한다.

| 책무 | 동작 |
| --- | --- |
| 예산 감시 | 참가자별 실제 부담액의 보수적 상단이 개인 상한을 초과하면 경보 → 이전 라운드 재조정 요청 |
| 라운드 간 모순 | 숙소는 우메다인데 액티비티가 전부 텐노지 → 재배치 요청 |
| **자동 재심** | 최소 만족도가 임계치 미만이면 해당 라운드 자동 재개최 (8.5절) |
| 공정성 감시 | 현재 Plan의 총 선호 손실도를 계산하고 그 전까지 동급인 대안만 보정 |
| 최종 검증 | 계획서 전체를 물리적 실현 가능성·예산·제약 관점에서 전수 점검 |
| 서명 | 최종 계획서에 판단 근거와 미해결 쟁점을 기록 |

## 7. 라운드 프로토콜 (토론 진행 규칙)

### 7.1 라운드 목록

목적지가 확정되어 있으므로 R0에서 목적지 협상이 빠진다. 대신 컨셉·페이스와 남은 예산을 사용할 요구의 우선순위에 집중한다. 분야별 예산은 미리 나누지 않는다.

| # | 라운드 | 심판 | 결정 사항 | 국내 |
| --- | --- | --- | --- | --- |
| **R0** | **프레이밍** | Chief | **일정 확정(★v1.2)** · 여행 컨셉·페이스·예산 항목별 배분·거점 지역 | ○ |
| R1 | 이동 | Flight / Transport | 항공(해외)/철도·자차(국내), 출도착 시간대, 현지 교통 | ○ |
| R2 | 숙소 | Accommodation | 지역, 숙소 타입, 방 배정, 박당 예산 | ○ |
| R3 | 액티비티 | Activity | 관광지·체험 셋 확정 (필수/선택 구분) | ○ |
| R4 | 식사 | Dining | 끼니별 식당 후보, 예약 필요 건 | ○ |
| R5 | 동선 배치 | Scheduler | 날짜·시간대 배치, 이동시간 검증 | ○ |
| R6 | 예산 정산 | Budget | 1인당 비용, 공동경비, 정산 방식 | ○ |

**국내 목적지의 R1 변형**: 항공 대신 KTX·고속버스·자차를 다룬다. 자차 선택 시 "운전자 지정"과 "유류비 분담"이 추가 쟁점이 된다. Destination Pack의 `roundPreset`이 이를 결정한다 (`standard_domestic` / `standard_overseas`).

R0·R6는 짧게(2~4턴), R2~R4는 길게(8~14턴) 배분한다.

### 7.2 DateResolver — 일정 자동 확정 (R0 전처리)

**날짜 결정은 토론이 아니라 계산이다.** LLM에게 캘린더 교집합을 맡기면 반드시 틀린다. 결정론적 알고리즘으로 후보를 뽑고, 후보가 여럿일 때만 R0에서 짧게 논의한다.

#### 7.2.1 알고리즘

```
입력: SurveySnapshot.activeParticipantIds 전원의 availability (가능일 비트맵, 불가일 비트맵)
      방에서 합의된 여행 일수 requiredTripDays
      Destination Pack (recommendedNights, peakSeasons, avoidDates, weatherProfile)

[1] 정규화
    각 참여자를 향후 180일 길이의 비트벡터로 변환
    available[i][d] = 1  if (가능일에 포함) and (불가일에 미포함)

[2] 여행 길이 결정
    L = requiredTripDays
    # 기간 축소는 전원 명시적 동의와 새 SurveySnapshot 없이는 적용 금지

[3] 교집합 슬라이딩 윈도우
    common[d] = bitwise_and_i(available[i][d])
    for d in 0..180-L:
        if all(common[d..d+L-1]):
            fullWindows.add(d)

[4] fullWindows가 비었을 때
    DATE_BLOCKED 반환
    # N-1, 최다 참석, 추정 날짜 산출 금지

[5] 스코어링 (fullWindows에 대해)
    Score(d) = 0.30 × 항공료지수(d)      # Amadeus Flight Cheapest Date Search
             + 0.20 × 요일적합도(d)      # 금~일 포함 시 가산, 휴가 소모 최소화
             + 0.20 × 개인선호합(d)      # 설문에서 '선호' 표시한 날 포함 비율
             + 0.15 × 계절·날씨(d)       # Pack.weatherProfile
             − 0.10 × 성수기페널티(d)     # Pack.peakSeasons (혼잡·가격)
             − 0.05 × 임박도페널티(d)     # 21일 이내 출발은 항공·숙소가 비싸다

[6] 상위 3개 구간을 후보로 R0에 전달
    Score 1위가 2위를 0.15 이상 앞서면 → 토론 생략, 즉시 확정
```

#### 7.2.2 항공료를 날짜 선정에 반영하는 이유

해외 여행에서 **날짜가 항공료의 최대 변수**다. 같은 오사카 3박이어도 출발일에 따라 1인 15만원 이상 차이가 난다. 예산이 빠듯한 그룹에게 이 차이는 숙소 등급 하나를 좌우한다.

따라서 DateResolver는 R0 이전에 Amadeus **Flight Cheapest Date Search**(`GET /v1/shopping/flight-dates`)를 호출해 후보 구간별 최저가 지수를 확보한다. 상세는 `flight-referee-implementation.md` 4.2절 참조.

국내 Pack은 항공 변수가 작으므로 항공료지수 가중치를 요일적합도로 이관한다 (0.30 → 요일 0.50).

#### 7.2.3 R0에서의 일정 안건 처리

| 상황 | 처리 |
| --- | --- |
| 후보 1개 | Chief가 확정 공지. 토론 없음 |
| 후보 2~3개, 점수차 ≥ 0.15 | 1위 확정 + 근거 공지. 토론 없음 |
| 후보 2~3개, 점수차 < 0.15 | 각 에이전트 1턴 발언 → Chief 판결 (최대 8턴) |
| 전원 가능 구간 없음 | `DATE_BLOCKED`; 날짜·기간·활성 인원 변경 전까지 후속 단계 금지 |

날짜 토론에서 에이전트의 논거는 개인 선호(주말 선호, 연차 아까움, 혼잡 기피)와 예산(항공료 차이)이다. 확정 즉시 **모든 후속 심판의 조회 파라미터**(`checkin`, `checkout`, `departureDate`)로 주입된다.

### 7.3 라운드 내부 진행 (7단계 상태머신)

실시간 제약이 없어지면서 v1.0의 **VOTING(사용자 투표)** 단계가 **REVIEW(Chief 자동 검토)** 로 대체된다.

```
[1] OPENING      심판이 라운드 목표·제약·배정 예산을 선언
        ↓
[2] SOURCING     Destination Pack 기반 API 호출 → 후보 카드 5~8장
                 (동일 Pack·동일 시기 캐시 우선 조회)
        ↓
[3] STATEMENT    각 참여자 에이전트 1턴씩 순차 발언
                 → 발언 순서는 결정론적 순환 방식 (선호 손실도로 발언권 변경 금지)
        ↓
[4] CLASH        오케스트레이터가 충돌축(conflict axis) 자동 추출
                 → 대립 진영 대표 2~3명만 2~3턴씩 반박
                 (전원 발언 금지: 비용·가독성 관리)
        ↓
[5] FACTCHECK    심판이 API 재조회로 쟁점 검증, 잘못된 주장 정정
        ↓
[6] PROPOSAL     심판이 절충안 1~2개 생성 → 각 에이전트 찬반 1턴
        ↓
[7] VERDICT      스코어링 → 판결문 작성
        ↓
[8] REVIEW ★     Chief가 자동 검토
                 - 최소 만족도 ≥ 임계치?
                 - 예산 배정 준수?
                 - 하드 제약 위반 0건?
                 - 이전 라운드와 모순 없음?
                 통과 → 다음 라운드
                 실패 → [4]로 회귀 (최대 2회, 사유를 회의록에 기록)
```

**턴 상한**: 라운드당 최대 32턴. 실시간 제약이 없으므로 v1.0(24턴/90초)보다 여유롭게 잡되, 비용 상한은 유지한다.

### 7.4 충돌축 자동 추출

전원이 매 턴 발언하면 6명 × 10턴 = 60회 LLM 호출로 비용이 폭발한다. 대신:

1. STATEMENT 결과를 후보별 지지 벡터로 변환
2. 코사인 유사도 클러스터링으로 2~3개 진영 구분
3. 각 진영에서 **가장 극단적인 1명**을 대표로 선출해 CLASH 참여
4. 나머지는 "👍 동의 (박서연)" 형태의 경량 반응 (LLM 호출 없음)

라운드당 LLM 호출 60% 절감 + 회의록 가독성 상승. 나중에 읽는 구조에서는 **읽기 부담이 곧 이탈**이므로 이 설계가 v1.0보다 더 중요해졌다.

### 7.5 회의록 가독성 설계

사용자가 실시간으로 보지 않는다는 것은 **한 번에 몰아 읽는다**는 뜻이다. 회의록은 문서로서 완결성을 가져야 한다.

- 라운드 상단에 **3줄 요약**을 먼저 배치 (읽지 않고 넘길 사람용)
- 각 발언에 발화자 아바타·양보지수 뱃지 표시
- 심판의 팩트체크는 별도 블록으로 시각 구분
- 판결문은 카드 형태로 강조
- **전체 회의록 예상 읽기 시간**을 표기 ("약 6분")
- 리플레이 모드: 타이핑 연출로 재생 / 배속 조절 / 라운드 점프

## 8. 합의 알고리즘

사용자가 개입할 수 없으므로, **이 알고리즘이 최종 품질을 전적으로 결정한다.** v1.0보다 안전 마진을 크게 잡는다.

### 8.1 스코어링 공식

> 현재 구현 기준: 이 절의 기존 `0~1` 속성 적합도와 아래 `0~10` 재심 임계치는 초기 설계안이다. MVP에서는 분야·세부 `5·3·1`과 `fulfillment = 0 / 0.5 / 1`을 이용해 참가자 만족도를 `0~100`으로 정규화한다. 여행 목적과 취향 점수는 분리하며, 목적급 항목은 점수로 상쇄하지 않는 별도 승인 게이트다. `TOGETHERNESS`에는 점수 하한을 적용하지 않고, `BALANCED`는 60점 목표·40점 미만 승인, `CONTENT_DRIVEN`은 목적 게이트와 60점 하한을 적용한다. 상세 계약은 [group-trip-survey-agent-backend.md](group-trip-survey-agent-backend.md#7-점수-계산)를 따른다.

일반 취향의 후보 순서는 `effectiveImportance = categoryPriority × detailImportance`로 만들고 `25 → 15 → 9 → 5 → 3 → 1` 계층을 차례로 비교한다. 같은 실효 중요도에서는 컨셉 중요도가 높은 분야를 먼저 보고, 그다음 사용자가 입력한 내부 순위를 적용한다. 목적급은 이 계산에서 제외해 항상 최상위 게이트로 처리하며 하위 계층 여러 개로 상위 계층의 손실을 상쇄하지 않는다.

목적급은 개별 항목마다 `FULL > APPROVED_SUBSTITUTE > UNMET`으로 비교하고 `UNMET`은 확정을 차단한다. 일반 취향은 각 실효 중요도 계층에서 참가자별 `TierSat`를 계산한다. 후보 간 최소 `TierSat` 차이가 `5%p` 이내면 평균 `TierSat`를 비교하고, 평균 차이도 `5%p` 이내면 다음 계층으로 이동한다. 내부 정책값은 `tierToleranceBp=500`이며 경계값도 동급이다. 해당 계층에 취향이 없는 참가자는 제외하고, 취향이 있지만 미반영이면 0으로 포함한다.

후보 `c`에 대한 참여자 `i`의 만족도:

```
Sat(i, c) = Σ_k ( w[i][k] × match(c, k) )  − penalty_soft_violation
            (k = 속성: 가격, 위치, 타입, 테마, 페이스 …)
```

- `w[i][k]`: 설문 슬라이더·카드 점수에서 유도한 개인 가중치 (정규화 0~1)
- `match(c,k)`: 후보 속성 적합도 (API 메타데이터 기반, 0~1)
- 하드 제약 위반 후보는 **스코어링 이전에 실격**

MVP의 실제 `fulfillment` 값은 Agent의 자연어 판단이 아니라 검증 코드가 확정한다. 일정 포함과 근거가 확인된 완전 일치는 `1`, 버전이 있는 카테고리 RulePack이 허용한 부분·대체 일치는 `0.5`, 일정 미포함·미검증·허용 규칙 부재는 `0`이다. 명시적 횟수 요구가 없는 동일 취향의 복수 매칭은 `max(fulfillment)`를 사용하며 합산하지 않는다. 목적급 항목의 `0.5`는 사용자 승인 전 목적 게이트를 통과시키지 않는다.

점수 결과는 `SCORED(valueBp)`와 `NOT_APPLICABLE(NO_PREFERENCES)`로 구분한다. 0점은 입력한 취향이 전혀 반영되지 않은 경우에만 사용한다. Maximin과 평균은 `SCORED` 참가자만 집계하며, 계산 가능한 참가자가 없으면 만족도 단계를 생략하고 하드 제약·목적·페이스·비용·동선·예약 가능성으로 후보를 비교한다.

동일 취향의 기본 목표 횟수는 1이다. 2회 이상 요청은 모든 활성 참가자가 명시적으로 동의한 경우에만 초기 `planningCount`에 적용한다. 한 명이라도 비동의하면 원래 `requestedCount`를 보존한 채 `planningCount=1`로 Plan v0를 생성하고 `DEFERRED_MULTIPLICITY` 쟁점으로 남긴다. 반영도는 원래 요청 대비 검증된 횟수가 0이면 `0`, 일부면 `0.5`, 전부면 `1`이다. 목적급 횟수의 부분 반영은 Plan v0에는 허용하지만 사용자 승인 전 최종 확정하지 않는다.

### 8.2 선택 기준: 평등주의 우선 + 총합 보조

단순 합계(공리주의)로 뽑으면 소수가 계속 희생된다. 여행 그룹에는 **최소 만족도 극대화(Maximin)** 가 적합하다.

```
1순위: max( min_i Sat(i, c) )              # 가장 불만족한 사람의 만족도 최대화
2순위: 동률 시 max( Σ_i Sat(i, c) )         # 총합
3순위: 동률 시 선호 손실도가 큰 참여자의 안을 우선    # 공정성 타이브레이커
4순위: 동률 시 비용·이동 Pareto 지배 후보 제거
5순위: 최대 개인 예산 사용률 → 최대 하루 이동시간 → 총비용 → 총이동시간
```

### 8.3 선호 손실도 (Preference Loss) — 보조 공정성 지표

```
PreferenceLoss(i, p)
= Importance(i, p) × (1 - Fulfillment(i, p))

ParticipantPreferenceLoss(i)
= Σ PreferenceLoss(i, p)
```

예시:

| 중요도 | 반영도 | 선호 손실도 |
| ---: | ---: | ---: |
| 5 | 1 | 0 |
| 5 | 0.5 | 2.5 |
| 5 | 0 | 5 |
| 3 | 0.5 | 1.5 |
| 1 | 0 | 1 |

선호 손실도는 실제 비용·벌금이 아니다. 만족도 자체를 변형하거나 참가자의 발언권·Proxy 말투를 바꾸지 않는다. 현재 Plan의 최종 결과를 기준으로 하드 제약, 목적급 게이트, 최소 만족도, Maximin, 평균 만족도와 스타일 적합도까지 동일한 대안 사이에서만 타이브레이커로 사용한다. 라운드 순서와 연속 손실 횟수는 계산하지 않는다.

`PreferenceLossLedger`는 모든 버전의 결정 이력을 보존하지만 현재 값은 현 Plan 버전에서 다시 계산한다. 같은 손실을 버전마다 중복 누적하지 않고, 일정이 개선되면 현재 손실도도 감소한다. `NO_PREFERENCE`는 제외하며 값은 여행이 끝나면 다음 여행으로 이월하지 않는다. 개인별 원점수는 다른 참가자에게 공개하지 않는다.

### 8.4 예산 제약 처리

- 그룹 평균이나 최저 예산자의 단일 상한 대신 각 참가자의 실제 부담액을 개인 예산 상한과 비교한다.
- 숙소·공동 이동·공용 예약비는 실제 이용자 균등 분담, 개인 교통·식사·액티비티는 참가자별 비용으로 계산한다.
- 개인 객실·좌석 업그레이드 차액은 요청자가 부담한다.
- 참가자 간 보조 분담은 관련 참가자 전원의 명시적 `CostSharingAgreement`가 있을 때만 허용한다.
- 가격 검사는 `확정 비용 + 미확정 비용 상단 + 예비비`를 사용하며 예비비율은 `max(10%, 공급자 불확실성 비율)`이다.
- 분야별 고정 예산을 두지 않는다. 필수 기본비와 예비비를 제외한 잔액을 `목적급 → 분야 중요도×세부 중요도 → 최저 만족도 → 비용 효율` 순으로 사용한다. 그 단계까지 동급인 요구에만 선호 손실도를 적용한다. 같은 충족도를 제공하면 더 저렴한 후보를 선택하고 잔액을 억지로 소진하지 않는다.
- 한 참가자라도 개인 상한을 넘으면 `BUDGET_BLOCKED`이며, 상한 변경은 해당 참가자의 직접 입력과 새 설문 스냅샷을 요구한다.

모든 선호 계층까지 동급이면 비용과 이동을 다음 순서로 비교한다. 모든 참가자의 비용과 최대·총 이동시간이 다른 후보보다 나쁘지 않은 Pareto 지배 후보를 먼저 남긴다. 이후 최대 개인 예산 사용률 차이가 `5%p`를 넘으면 낮은 후보, `5%p` 이내면 최대 하루 이동시간을 본다. 최대 하루 이동시간 차이가 `30분`을 넘으면 짧은 후보, 이내면 총비용과 총이동시간 순서로 비교한다. 정책값은 `budgetUtilizationToleranceBp=500`, `maxDailyTravelDifferenceToleranceMinutes=30`이며 경계도 동급이다. 30분은 후보 간 차이 허용값이고 실제 하루 이동 상한은 체력·접근성 하드 제약으로 별도 검증한다.

총비용과 총이동시간까지 동급이면 예약·검증 신뢰도를 가중합하지 않고 `필수 필드 완전성 → 실행 준비 상태 → 핵심 근거 최소 출처 등급 → 핵심 근거 최소 남은 TTL → non-degraded → 선택 필드 커버리지 → canonical ID` 순으로 비교한다. 예약 필요 후보는 `BOOKABLE`, 예약 불필요 후보는 영업·운영을 확인한 `VERIFIED` 이상이어야 한다. 가격·재고·예약 가능성 근거는 공식 홈페이지·계약 OTA 이상인 출처 등급 2를 요구한다. 핵심 근거가 여러 개면 평균이 아닌 최솟값을 사용한다. LLM 확률·근거 개수·리뷰 수는 신뢰도에 넣지 않으며 `BOOKED`는 사용자 예약 이벤트만 생성한다.

### 8.5 Chief 자동 재심 (사용자 승인 투표의 대체물)

라운드 판결 후 Chief가 다음 조건을 검사한다. 하나라도 걸리면 CLASH 단계로 자동 회귀한다.

| # | 재심 조건 | 임계치 |
| --- | --- | --- |
| C1 | 목적 유형별 최소 만족도 미달 | `BALANCED`: `< 60` 재탐색·재토론, `< 40` 사용자 확인. `CONTENT_DRIVEN`: `< 60` 미통과 |
| C2 | 만족도 격차가 과대 | `SatisfactionGapBp > 2500`일 때 최저 만족도 참가자의 미반영 분야만 1회 재토론. `NOT_APPLICABLE` 제외, `SCORED` 2명 미만이면 생략 |
| C4 | 개인 예산 상한 초과 | 참가자 1명이라도 `BudgetCheckAmount > PersonalBudgetCap` |
| C5 | 하드 제약 위반 | 1건이라도 |
| C6 | 이전 라운드와 모순 | 지역 불일치 등 |
| C7 | 후보 검증 실패 | 존재하지 않는 항목 참조 |

- 일반 재심은 최대 2회지만 C2 공정성 재토론은 최대 1회다. C2가 남으면 검증된 최선안과 양보 내역을 제시하고, 목적급·5점 전체 미반영·최소 만족도 미달이면 별도 사용자 확인 정책을 적용한다.
- 재심 발생 사실과 사유는 사용자에게 그대로 노출한다 → "AI가 대충 하지 않았다"는 신뢰 신호
- C5·C7은 재심이 아니라 **즉시 실격 후 재조달(re-sourcing)**

Proxy Agent는 각 협상안에 `SUPPORT | ACCEPTABLE | OPPOSE | USER_CONFIRMATION_REQUIRED`로 투표한다. 전원 `SUPPORT` 또는 `ACCEPTABLE`이고 모든 코드 검증을 통과할 때만 Agent 합의로 본다. 최초 협상안과 수정안 2개까지 총 3회 투표하며 다수결은 사용하지 않는다.

최대 수정 후에도 일반 3점·1점 취향이나 단순 대안 선호만 충돌하면 Maximin과 확정된 계층식 타이브레이커로 선택하고 이견을 기록한다. 하드 제약 위반안은 폐기한다. 목적급·5점 전체 미반영·최소 만족도 미달은 차선책을 자동 채택하지 않고 관련 사용자에게 검증된 대안을 제시한다. 동일 쟁점의 사용자 요청 재개는 최대 2회이고 세 번째부터는 검증된 선택지 중 직접 선택하도록 한다.

### 8.6 사후 재개최 (Rerun)

결과 확인 후 불만이 있을 때의 유일한 회복 경로.

```
[결과 화면]
  🏨 숙소: 호텔 A 2박 + 료칸 B 1박
     └ [ 이 결정 다시 논의하기 ]

  ↓ 선택 시
  재개최 옵션
   ○ 조건 추가하고 다시 (예: "예산 10만원 더 쓸게요")
   ○ 후보를 바꿔서 다시 (다른 지역 요청)
   ○ 그냥 다시 (다른 결과가 나올 수 있음)

  → 방장 승인 필요 · 방당 2회 무료
  → 해당 라운드 이후 라운드는 연쇄 재실행
```

재개최는 개입이 아니라 **결과에 대한 사후 액션**이므로 "설문 내고 방치" 원칙을 깨지 않는다. 다만 R2를 재실행하면 R3~R6이 연쇄 재계산되므로 비용이 크다. 무료 횟수를 제한하고, 유료 플랜의 핵심 혜택으로 둔다.

## 9. 카테고리별 심판 에이전트 × API 매핑

> ⚠️ **주의**: 아래 API들의 요금제·이용약관·쿼터는 수시로 변경된다. 착수 전 각 제공자의 최신 문서와 상업적 이용 조건을 반드시 재확인할 것. 특히 한국 숙박·일본 미식 분야는 공개 API가 제한적이라 대체 전략이 필요하다.

**목적지 확정의 이점**: 각 심판은 Destination Pack의 `providers` 배열을 그대로 우선순위로 사용한다. 지역별 분기 로직이 코드에서 사라진다.

**상세 구현 문서**: 항공권·교통편·숙소 심판은 API 스펙·도구 정의·주장 강도 추정·시스템 프롬프트 전문을 별도 문서로 분리했다.

| 용도 | API |
| --- | --- |
| 지점 간 이동시간 행렬 | Google Distance Matrix API |
| 대중교통 상세 경로 | ODsay(한국), NAVITIME(일본) |
| 일출·일몰 | Sunrise-Sunset API |
| 날씨 예보 | 기상청 / OpenWeather |

**판정 기준**: 하루 총 이동시간 상한(페이스 연동), 도보 거리 상한(체력 제약), 영업시간 충돌, 식사 시간 확보, 동선 역행 최소화.

**알고리즘**: LLM만으로 동선을 짜면 반드시 실수한다. MVP는 **결정론적 제약 우선 Beam Search + LLM 힌트·설명** 조합을 사용한다.

1. 하드 제약 위반 후보 제거
2. 항공·도시간 교통·체크인·고정 예약을 앵커로 배치
3. 목적급 콘텐츠 우선 배치
4. 날짜·지역별 후보 클러스터 구성
5. 15분 슬롯에서 `beamWidth=30`으로 탐색
6. 상위 일정안 3개를 확정된 계층식 공정성 순서로 비교
7. 영업시간·도보 상한·페이스·예산을 `PlanValidator`로 검증

분야·날짜별 후보는 최대 10개다. 페이스별 하루 주요 콘텐츠는 휴식형 1개, 평균형 2개, 활동형 3개이며 식사·숙소 체크인·체크아웃·단순 이동은 제외한다. 대중교통·도보 이동 버퍼는 `max(10분, 예상 이동시간의 20%)`다. 항공·도시간 교통의 도착 여유는 분야별 하드 규칙으로 별도 계산한다. Scheduler Agent는 지역 묶음과 일정 테마를 제안할 수 있지만 실제 시간·이동·예산 계산과 최종 선택은 코드가 담당한다.

목적지 확정 덕분에 **이동시간 행렬을 Destination Pack 단위로 프리컴퓨트**할 수 있다. 주요 POI 200개 × 200개 행렬을 미리 캐싱해두면 R5 실행시간과 API 비용이 크게 줄어든다.

### 10.2 실행 신뢰성 — 비동기의 대가

사용자가 지켜보지 않으므로 **실패가 조용히 발생한다.** 이것이 비동기 모델의 가장 큰 운영 리스크다.

| 장치 | 내용 |
| --- | --- |
| 체크포인트 | 라운드 단위로 상태 저장. 실패 시 해당 라운드부터 재개 |
| 재시도 | LLM/API 호출 실패 시 지수 백오프 3회, 이후 폴백 제공자 |
| 타임아웃 | 방 전체 실행 30분 상한. 초과 시 부분 결과 + 사유 안내 |
| 부분 실패 처리 | R4 실패 시 R1~R3 결과로 "부분 계획서" 발행 후 재시도 예약 |
| 실패 알림 | 사용자에게 정직하게 통지 + 자동 재실행 예약 (침묵 금지) |
| 데드레터 큐 | 3회 실패 잡은 DLQ로 이동, 운영 대시보드에 알림 |
| 멱등성 | 잡 ID 기반. 중복 실행되어도 결과 1개만 발행 |

### 10.3 Data Gateway·Provider Connector — 글로벌 확장의 핵심

Destination Pack이 제공자 우선순위를 결정한다. Provider Connector는 외부 API 호출만 담당하고, Data Gateway가 캐시·폴백·표준 스키마 정규화·근거 저장·TTL을 강제한다. 둘 다 LLM Agent가 아니다.

탐색용 캐시와 확정용 TTL은 분리한다. 확정용 TTL은 항공 가격·좌석 10분, 숙소 가격·객실 15분, 식당·액티비티 예약 가능 여부 30분, 영업시간·대중교통 시간표 24시간, 예상 이동시간 6시간, 장소 기본정보와 미디어·평판 7일이다. 최종 일정 직전에 미디어·평판을 제외한 변동 데이터를 일괄 재검증하며 후보별 재시도는 최대 2회다. `PARTIAL`에서 가격·가용성·영업·날짜·운영시간·위치·알레르기 안전·접근성 필드가 누락되면 fail-closed로 차단한다. 가격 변동이 5% 이내면 최신 가격으로 예산을 다시 계산하고, 5%를 넘으면 대체 후보와 재비교한다. 개인 예산 상한 초과는 항상 `BUDGET_BLOCKED`다.

```typescript
interface HotelConnector {
  readonly id: string;
  supports(pack: DestinationPack): boolean;
  search(q: HotelQuery): Promise<ProviderResult<HotelCandidate[]>>;
}

// Pack이 우선순위를 제공. 실패 시 다음 제공자로 폴백
const providers = registry.resolve('hotel', room.packId);
// jp-osaka → [RakutenTravel, AmadeusHotel, GooglePlaces]
// kr-gangneung → [AmadeusHotel, GooglePlaces]
```

**정규화 스키마 (HotelCandidate 예시)**

```json
{
  "id": "H-03",
  "source": "rakuten_travel",
  "name": "難波ホテル",
  "type": "hotel",
  "location": { "lat": 34.665, "lng": 135.501, "area": "난바" },
  "price": { "perNightPerPerson": 52000, "currency": "KRW", "confidence": "live" },
  "capacity": { "maxGuests": 6, "roomConfig": "2인실 × 3" },
  "amenities": ["breakfast", "no_smoking", "luggage_storage"],
  "rating": { "score": 4.4, "count": 1203 },
  "accessibility": { "wheelchair": false, "elevator": true },
  "cancelPolicy": "3일 전 무료",
  "bookingUrl": "https://…",
  "images": ["…"]
}
```

**에이전트와 심판은 원본 API 형식을 절대 보지 않는다.** 이것이 확장성과 프롬프트 안정성을 동시에 보장한다.

### 10.4 회의록 리플레이

실시간 스트리밍은 없지만 몰입감은 유지한다.

- 저장된 메시지 시퀀스를 클라이언트에서 타이핑 연출로 재생
- 배속(1x / 2x / 즉시 전체 보기), 라운드 점프, 특정 인물 발언만 필터
- 실시간 생성보다 **연출 통제가 쉽다** — 극적인 순간(팩트체크, 판결)에 의도적 pause 삽입 가능
- 서버 부하 없음 (정적 데이터 재생)

### 11.2 상태 전이

```
room:   DRAFT → COLLECTING → DATE_RESOLVING → READY → QUEUED → RUNNING → COMPLETED → ARCHIVED
                              ↘ DATE_BLOCKED (전원 가능 구간 없음)
                                 └→ 날짜·기간·활성 인원 명시적 변경 → 새 Snapshot → DATE_RESOLVING
                                              ↘ FAILED → (자동 재시도) → QUEUED
                                              COMPLETED → RERUN_REQUESTED → QUEUED

round:  PENDING → SOURCING → STATEMENT → CLASH → FACTCHECK
        → PROPOSAL → VERDICT → REVIEW
        (REVIEW 실패 → CLASH로 회귀, rerun_count++, 최대 2회)
```

v1.0 대비 변경점: `DEBATING`이 `QUEUED`/`RUNNING`으로 분리, 라운드의 `VOTING` 제거·`REVIEW` 신설, `runs` 테이블 신설(재개최 이력 관리).
v1.1 대비 변경점: `DATE_RESOLVING`/`DATE_BLOCKED` 상태 신설, `date_resolutions` 테이블 추가, `rooms`에서 날짜·인원·예산 컬럼 제거.

## 12. LLM 비용·배치 최적화

비동기 전환의 가장 큰 실익은 **원가**다. 실시간 응답 의무가 없으면 배치 처리로 넘길 수 있다.

### 12.1 목표 원가

| 항목 | v1.0(실시간) | **v1.1(배치)** |
| --- | --- | --- |
| 방 1개(6명, 7라운드) LLM 비용 | $0.4 ~ $0.8 | **$0.2 ~ $0.45** |
| 외부 API 비용 | — | Pack 캐시로 70% 절감 |
| 총 실행 시간 | 4~7분 (관전 속도 제약) | 5~20분 (제약 없음) |
| 총 LLM 호출 | 70~110회 | 70~110회 (단가 하락) |

### 12.2 최적화 전략

1. **배치 API 활용** — 실시간 응답이 불필요하므로 비동기 배치 엔드포인트로 처리. 동일 라운드의 참여자 1차 발언(STATEMENT)은 6건을 한 배치로 제출
2. **모델 티어링**
   - 참여자 에이전트 발화 → 소형·저가 모델 (짧고 캐릭터성 위주)
   - 심판 판결·팩트체크·절충안 → 중대형 모델 (추론 필요)
   - Chief 검토·최종 문장화 → 중형 모델
3. **프롬프트 캐싱** — 페르소나 카드, 후보 카드, 라운드 규칙은 라운드 내내 불변 → 캐시 접두부 고정
4. **발언자 축소** — 충돌축 대표 발언 방식으로 호출 60% 절감
5. **경량 반응** — 비발언자 동의/반대는 스코어링 엔진이 계산, LLM 미사용
6. **결정론적 계산 분리** — 스코어링·예산 합산·동선 최적화는 전부 코드로 (LLM은 산술에 취약하고 비싸다)
7. **Destination Pack 캐시** — 동일 Pack·유사 날짜의 후보 조회 결과를 방 간 공유 (6~24시간 TTL). 목적지 확정형이라 가능해진 최적화
8. **프리컴퓨트** — 인기 Pack의 POI 이동시간 행렬·후보 풀을 배치로 미리 계산
9. **출력 길이 강제** — 발화 max_tokens 120, 판결문 400
10. **조기 종료** — 3턴 연속 후보 순위 불변이면 수렴으로 간주하고 즉시 판결

### 12.3 컨텍스트 압축

라운드 종료 후 대화 전문은 DB에 남기되, 다음 라운드 컨텍스트에는 **판결 요약 3줄 + 확정 항목**만 전달한다. 전체 로그를 계속 넘기면 R5쯤 컨텍스트가 폭발한다.

### 12.4 비용 가드레일

- 방당 토큰 하드 캡 설정. 도달 시 남은 라운드는 축약 모드(발언 축소·즉시 판결)
- 재개최는 비용이 크므로 무료 2회 제한 + 유료 플랜 혜택
- `llm_usage` 원장으로 방 단위 원가를 실시간 추적, 이상치 알림

### 16.1 포지셔닝에 대한 메모

개입할 수 없는 서비스는 **"완벽한 계획을 만들어준다"고 약속하면 안 된다.** 약속을 지킬 수 없고, 한 번의 실망이 곧 이탈이다.

올바른 약속은 이것이다:

> **"모두의 의견이 반영된 납득 가능한 초안을, 아무도 고생하지 않고 얻는다."**

이 프레이밍이면 사소한 흠결은 용인되고, 재개최는 자연스러운 다음 단계가 된다.

## 18. 글로벌 확장 계획

### 18.1 확장 단위 = Destination Pack

v1.1에서 목적지가 확정형이 되면서 확장의 단위가 명확해졌다. **"국가 진출"이 아니라 "Pack N개 추가"** 다.

| 등급 | 정의 | 제공 기능 |
| --- | --- | --- |
| **A (Full)** | 숙소 실시간 + 로컬 미식 + 대중교통 상세 | 전 라운드 정밀 모드 |
| **B (Standard)** | 글로벌 API로 커버, 로컬 데이터 부족 | 밴드 가격, 이동시간 추정 |
| **C (Lite)** | Places + 위키 수준 | 액티비티·동선만, 숙소는 링크아웃 |

MVP: 한국 5 + 일본 6 = 전부 A등급.

### 18.2 Pack 제작 파이프라인

확장 속도는 Pack 제작 비용이 결정한다. 이를 반자동화하는 것이 확장 전략의 핵심이다.

```
[1] 후보 도시 선정      ← "요청하기" 버튼 수요 데이터 + 항공 노선 데이터
[2] 제공자 커버리지 조사  ← 자동: 해당 도시로 각 API 테스트 호출, 응답 품질 스코어링
[3] 등급 판정 (A/B/C)   ← 자동
[4] 카드덱 초안 생성     ← 반자동: Places 인기도 + 리뷰 수 + 카테고리 다양성으로 20장 후보 추출
[5] 로컬 검수          ← 수동: 현지 지식 보유자 or 리서처가 카드덱·config 검수  ★ 병목
[6] config 작성        ← 반자동: 통화·식사시간·팁 문화는 국가 템플릿 상속
[7] 파일럿 운영         ← 내부 테스트 방 5개 실행, 결과 품질 검수
[8] 오픈
```

**[5] 로컬 검수가 유일한 수동 병목이다.** Phase 4부터는 커뮤니티 기여형으로 전환해 이 비용을 분산한다.

### 18.3 단계별 로드맵

**Phase 3 — 동아시아·동남아 (출시 후 6~9개월)**

- 목표: Pack 25개
- 대상: 대만(타이베이), 홍콩, 태국(방콕·치앙마이), 베트남(다낭·호치민), 싱가포르, 일본 추가(나고야·오키나와·가나자와)
- 신규 어댑터: Agoda/Booking(숙소 강세), Klook(액티비티 강세), Google Transit
- 과제: 로컬 미식 데이터 부족 → Google Places 리뷰 + 자체 큐레이션 보강 (대부분 B등급)
- 다국어: 영어 UI 추가, 계획서 다국어 출력

**Phase 4 — 유럽·북미 (12~18개월)**

- 목표: Pack 60개
- 신규 어댑터: Booking.com / Expedia(EPS), Yelp(북미 식당), GetYourGuide, Rome2Rio(도시간 이동), Transitland/GTFS
- **신규 라운드 검토**: 철도패스·렌터카 라운드 (유럽 여행의 핵심 결정) → `roundPreset: "europe_multicity"`
- 멀티시티 Pack 본격화 (파리→니스, 로마→피렌체 등)
- 통화·세금·팁 문화 반영

**Phase 5 — 글로벌 롱테일 (18개월+)**

- OpenStreetMap / OpenTripMap / Wikivoyage 기반 **C등급 Pack 자동 생성**
- **커뮤니티 Pack** — 지역 크리에이터가 카드덱·팁을 제작하고 수익 배분. [5] 로컬 검수 병목 해소
- 언어별 페르소나 톤 현지화 (일본어의 완곡 어법, 영어의 직설적 협상 등)
- Pack 품질 평가 시스템 — 사용자 만족도 데이터로 Pack별 등급 자동 조정

### 18.4 확장을 위해 지금 해야 할 설계 결정

MVP 단계에서 지키지 않으면 확장 비용이 폭발한다.

1. **모든 외부 데이터는 정규화 스키마를 거친다.** 프롬프트에 원본 JSON을 절대 넣지 않는다.
2. **지역 의존 로직은 전부 `destination_packs` 테이블로.** 코드에 `if (country === 'JP')` 를 쓰는 순간 확장은 끝난다.
3. **프롬프트는 언어와 분리한다.** 시스템 프롬프트는 영어 템플릿 + `output_language` 파라미터.
4. **카드덱은 데이터다.** DB에 저장해 Pack 추가 시 배포 없이 확장.
5. **심판은 카테고리로 정의하되 도구는 Pack이 주입한다.** 숙소 심판 프롬프트는 하나, 도구는 Pack에 따라 교체.
6. **라운드 구성도 Pack이 결정한다.** `roundPreset`으로 국내/해외/유럽 멀티시티를 분기.

```typescript
// Pack이 늘어나도 심판 코드는 그대로
const pack = await packRegistry.get(room.packId);
const referee = createReferee('accommodation', {
  tools: registry.resolve('hotel', pack),
  config: pack.config,
  outputLanguage: room.language,
});
```

### A.2 숙소 심판 에이전트

```
당신은 여행 계획 회의의 **숙소 담당 심판**입니다.
공정하고, 데이터에 근거하며, 참여자의 감정보다 사실을 우선합니다.

## 중요: 참여자들은 이 회의에 실시간으로 개입할 수 없습니다.
그들은 설문만 내고 결과를 나중에 확인합니다.
따라서 당신의 판결이 최종에 가깝습니다. 추측하지 말고 반드시 도구로 확인하세요.

## 여행지 정보
{destination_name} ({pack_id})
주요 지역: {pack.areas}
현지 정보: {pack.config}

## 권한
- 도구를 사용해 실제 숙소 후보를 조회할 수 있습니다.
- 후보를 발명할 수 없습니다. 도구 응답에 존재하는 항목만 제시하세요.
- 하드 제약을 위반하는 후보를 실격 처리합니다.
- 당신의 판결은 총괄 심판(Chief)의 검토를 거칩니다.

## 사용 가능한 도구
- search_hotels(area, checkin, checkout, guests, price_max, type, amenities)
- get_travel_time(from, to, mode)
- get_place_details(place_id)

## 그룹 제약 (절대 위반 불가)
{hard_constraints}
숙소 항목 배정 예산: 1인 총액 {budget_allocated}원

## 판정 기준 (가중치)
1. 하드 제약 충족 (필수 — 위반 시 즉시 실격)
2. 1인 박당 가격이 배정 예산 내인가 (35%)
3. 주요 활동 지역까지 이동시간 (25%) — 반드시 get_travel_time으로 실측
4. 그룹 인원 수용 가능 여부 및 방 구성 (20%)
5. 평점 및 리뷰 수 (10%)
6. 취소 정책 유연성 (10%)

## 진행 절차
- SOURCING: 제약을 쿼리로 변환해 후보 5~8개를 조회하고,
  각 후보를 한 줄 요약과 함께 게시하세요.
  하드 제약 위반 후보는 실격 사유와 함께 표시하세요.
- FACTCHECK: 참여자가 사실관계를 틀리게 말하면 즉시 정정하세요.
  추측하지 말고 도구로 확인한 내용만 말하세요.
- PROPOSAL: 의견이 갈리면 절충안(숙소 분할, 등급 조정 등)을 제시하세요.
- VERDICT: 아래 형식으로 판결하세요.
```

### A.3 총괄 심판(Chief) — 자동 재심 게이트

```
당신은 전체 회의의 총괄 심판입니다.
참여자들이 회의에 개입할 수 없으므로, 품질을 보증하는 최종 책임은 당신에게 있습니다.

## 라운드 판결 검토 (REVIEW 단계)
다음 조건을 검사하고, 하나라도 걸리면 재심(CLASH 회귀)을 명령하세요.

C1  최소 만족도 < 5.0
C2  SCORED 만족도 격차(max−min) > 2500bp(25%p)
C4  참가자별 보수적 부담액이 개인 예산 상한을 초과
C5  하드 제약 위반 1건 이상          → 재심이 아니라 즉시 재조달(re-sourcing)
C6  이전 라운드 결정과 모순
C7  존재하지 않는 후보를 참조         → 즉시 재조달

재심은 라운드당 최대 2회입니다. 단, C2 공정성 재토론은 최저 만족도 참가자의 미반영 분야만 최대 1회입니다.
2회 후에도 미충족이면 차선책을 채택하고, 미해결 쟁점으로 기록하세요.

## 상시 감시 항목
1. 개인별 예산: 확정 비용·미확정 상단·예비비를 합친 부담액이 각자의 상한을 넘는가?
   → 초과 참가자와 금액, 줄일 수 있는 라운드를 구체적으로 제안
2. 라운드 간 모순: 숙소 위치와 액티비티 지역이 어긋나는가?
3. 공정성: 현재 Plan에서 특정 참여자의 총 선호 손실도가 큰가?
   → 그 전까지 동급인 대안에서만 해당 참여자의 안을 우선 검토
4. 실현 가능성: 확정된 일정이 물리적으로 가능한가?

## 출력 형식
{"decision": "pass|rerun|resource",
 "triggered": ["C1", "C4"],
 "reason": "참여자에게 그대로 보여줄 설명",
 "instruction": "재심 시 심판에게 줄 구체적 지시"}

## 원칙
- 재심 사유는 반드시 참여자에게 공개됩니다. 이해할 수 있는 말로 쓰세요.
- 통과시키기 애매하면 재심을 명령하세요.
  참여자가 고칠 수 없으므로, 의심스러울 때 넘어가는 비용이 훨씬 큽니다.
```

## 마무리 — 성공을 가르는 3가지

1. **설문이 전부다.** 개입 채널이 없으므로 설문에서 잡지 못한 제약은 영원히 반영되지 않는다. 특히 "절대 불가" 항목과 페르소나 확인 게이트에 제품 역량을 집중해야 한다. 이 두 화면의 완성도가 서비스 품질의 상한을 결정한다.

2. **환각 한 번이면 끝이다.** 존재하지 않는 료칸을 추천하는 순간 신뢰는 회복 불가다. 사용자가 실시간으로 걸러줄 수 없으므로 Validation Pass가 v1.0보다 훨씬 중요하다. 후보는 API 응답에서만, 계획서 발행 전 전수 검증.

3. **공정성이 제품의 정체성이다.** Maximin, 선호 손실도, 최소 만족도, 소수 의견 기록은 부가 기능이 아니다. 선호 손실도는 핵심 점수에 섞지 않고 현재 Plan의 동점 보정에만 제한한다.

## 19. v1.3 실행 보강 — 전역 계획·검증·협업 계약

> 이 장은 기존 설명 중 실행 책임이 모호했던 부분을 보강하는 **권위 있는 계약**이다. 같은 주제에서 이 장과 예시가 충돌하면 이 장을 우선한다. Activity, Dining, Scheduler, Budget, Chief의 개별 상세 구현은 담당 팀이 작성하되, 이 장의 공통 계약은 모든 라운드에 적용한다.

## 19.1 용어·책임 정합성

- **Round**는 R0~R6의 의사결정 단계다. R1에는 Flight와 Transport라는 두 referee instance가 있을 수 있다.
- **Category**는 flight, transport, accommodation, activity, dining, scheduler, budget의 도메인이다.
- **Referee instance**는 한 round/category를 실행하는 심판 프로세스다. Chief는 메타 검증자이며 일반 category 심판 수에 포함하지 않는다.
- R0의 거점 지역은 `provisionalAreaPreference`다. R2 Accommodation만 `areaDecision`을 최종 확정할 수 있다.
- `Must` 목록의 `[x]`는 구현 완료 표시가 아니다. 앞으로는 `설계/구현/검증` 상태 매트릭스로 관리한다.
- Pack 등급 A는 숙소 가격·로컬 미식·대중교통 상세가 모두 현재 데이터로 검증 가능한 경우에만 사용한다. 한국 숙소처럼 가격이 밴드 추정인 Pack은 기본 B이며, 실시간 가격 제휴가 확보될 때 A로 승격한다.

## 19.2 Preference & Mandate Contract

페르소나 카드 확인 단계는 단순 요약 확인이 아니라 사용자가 대리인에게 협상 권한을 위임하는 계약이다. 모든 항목은 `hard`, `strong_preference`, `negotiable`, `user_confirmation_required`, `new_survey_snapshot`과 privacy label을 가진다.

```json
{
  "userId": "u_882",
  "hard": ["no_red_eye", "crustacean_safe_only", "total_budget_lte_900000"],
  "strongPreferences": ["one_onsen_visit", "daily_walk_lte_6km"],
  "negotiableRanges": {
    "hotelTransitExtraMinPerDay": 15,
    "foodBudgetExtraKrw": 10000
  },
  "userConfirmationRequired": ["booked_item_change", "cost_sharing_change", "objective_degraded"],
  "newSurveySnapshot": ["date_change", "destination_change", "personal_budget_cap_change"],
  "privacy": {
    "roomingPreferences": "private",
    "healthAndBeliefDetails": "private"
  }
}
```

변경은 `AUTO_REPLAN → PROXY_DELEGATED → USER_CONFIRMATION_REQUIRED → NEW_SURVEY_SNAPSHOT` 순으로 권한을 분류한다. Agent는 사유와 대안만 제안하고, Orchestrator 코드가 공통 `ChangeAuthorityPolicy`로 결정한다.

- `AUTO_REPLAN`: 미예약·개인 예산 상한 이내·목적급과 최소 만족도 유지·검증 비하락 조건에서 영향 노드만 재계획한다.
- `PROXY_DELEGATED`: 3점 조건부 양보와 5점 일부 조정을 설문 위임 범위에서 처리한다.
- `USER_CONFIRMATION_REQUIRED`: 목적급 훼손, 모든 5점 미반영, 최소 만족도 미달, 비용 분담, 게시된 최종안의 실질 변경, BOOKED 변경, 취소·중복 예약 위험, 핵심 시간 속성·검증 상태 하락에 사용한다. 변경 전후 비용·이동시간·만족도·예약 영향을 영향받는 참가자에게 보여준다.
- `NEW_SURVEY_SNAPSHOT`: 날짜·기간·여행지·활성 참가자·개인 예산 상한·하드 제약·목적급과 같은 설문 기반 조건을 바꿀 때 사용한다. 기존 스냅샷은 보존한다.

승인 대기 중에는 해당 변경을 `AWAITING_USER`로 유지하며 자동 확정하지 않는다. 사용자 승인도 하드 제약이나 fail-closed 검증을 우회할 수 없다.

## 19.3 전역 Planning Graph와 수렴 규칙

여행은 독립 라운드의 단순 연쇄가 아니다. 다음 노드를 버전·입력 해시·근거·상태와 함께 저장한다.

```text
Date → Flight ─┬→ Accommodation Area → Accommodation
               ├→ Mobility Policy ───┐
               └→ Budget Snapshot ───┼→ Activity / Dining → Schedule
Accommodation ────────────────────────┘                  ↓
                                             Pass / Budget / Booking Readiness
```

각 노드는 `{nodeId, version, inputHash, dependencyVersions, status, confidence, evidenceRefs}`를 가진다. 상위 노드가 바뀌면 하위 노드는 삭제하지 않고 `STALE`로 전환한다.

```text
PROVISIONAL → VERIFIED → BOOKABLE → BOOKED
     └──────────────→ BLOCKED
     └──────────────→ STALE → 재계산
     └──────────────→ FAILED → 대체 후보 또는 사용자 안내
```

- R1의 교통패스는 R3/R5 결과로 재계산한다. 값이 바뀌어 예산·숙소·시간 제약을 침범하면 Chief에만 알리는 것으로 끝내지 않고 영향을 받는 노드를 `STALE` 처리한다.
- R2 숙소 변경 시 Activity, Dining, Schedule, 교통패스, Budget을 재계산한다.
- 재계산은 `최대 3회` 또는 후보 순위·하드 제약·총비용이 안정화될 때까지 수행한다. 수렴하지 않으면 최선의 검증 가능 계획과 충돌 설명을 `BLOCKED` 상태로 제시한다.
- 수동 확정·예약 완료 노드는 잠긴다. 이를 바꾸려면 취소 비용·대체 예약 위험·영향 범위를 먼저 보여주고 사용자 승인을 받아야 한다.

## 19.4 전역 일정 최적화 계약

R5의 그리디/2-opt는 후보 순서의 초기 해일 뿐, 계획의 실행 가능성 판정은 결정론적 제약 최적화기가 담당한다. optimizer는 검증된 top-K 전체 계획을 만들고, Maximin은 이 전역 계획 집합에서 선택한다.

필수 제약: 시간대와 IANA timezone, 운영시간·휴관일, 입장·식사 예약 슬롯, 체류시간, 공항·입국·수하물·체크인 버퍼, 식사 간격, 막차, 도보·계단·피로 상한, 체크인/아웃·짐 보관, 날씨 대체, 분할 숙박 이동, 예산, 예약 상태다. 모든 시간은 `timestamp + timezone + confidence`로 저장하며, 단순 HH:MM 문자열만으로 물리적 실행 가능성을 판단하지 않는다.

## 19.5 Negotiation Causality Ledger

토론은 연출이 아니라 검증된 탐색을 변경해야 한다. 모든 실질 발언과 심판 반박은 아래 구조로 저장하고 결과 화면에서 요약한다.

```json
{
  "claimId": "clm_104",
  "speaker": "persona:u_882",
  "claim": "하루 8km 도보는 수용할 수 없다",
  "evidenceRefs": ["survey.mobility.maxWalkKmPerDay", "route.ttm_v4"],
  "affected": {"constraint": "daily_walk_km", "previous": 8.0, "required": 6.0},
  "counteroffer": "5km 이후 조건부 택시와 예비비 추가",
  "recalculation": {"minSatisfaction": [4.8, 6.7], "budgetDeltaKrw": 3000},
  "planEffect": "Day 2 저녁 이동을 taxi로 변경"
}
```

발언 강도는 쟁점 식별·대안 설계·최소 만족도 하한에만 사용한다. 후보 선택은 검증된 만족도·하드 제약·불확실성을 반영한 Maximin으로 한다. CC는 라운드 종료 후의 공정성 원장 및 명시된 동점 해소에만 적용하며, 발언 순서·강도·최종 점수에 중복으로 가중하지 않는다.

## 19.6 증거, 불확실성, fail-closed 정책

모든 공급자 데이터는 `{source, retrievedAt, validUntil, confidence, termsRef}`를 포함한다. 만족도와 비용은 단일값이 아니라 추정 구간과 confidence를 보존하며, Maximin은 불확실성이 큰 후보에 robust penalty를 적용한다. C2 초기 정책값은 `2500bp(25%p)`이며 사후 여행 만족도·재실행·실패 데이터를 이용해 버전 단위로 보정한다.

| 필드 유형 | 검증 실패 시 정책 |
| --- | --- |
| 가격·리뷰·일반 이동시간 | 추정 허용. 범위·조회시각·신뢰도 표기 |
| 그룹 수용 인원·객실 조합 | **fail-closed**. winner/BOOKABLE 금지 |
| 알레르기·식이 안전, 휠체어·계단 접근성 | **fail-closed**. winner/BOOKABLE 금지 |
| 필수 영업 여부·예약 시간 슬롯·막차 | **fail-closed** 또는 검증된 안전 대체안 필수 |
| 취소·변경 조건 | 미확인 시 BOOKABLE 금지, VERIFIED에는 경고 가능 |

따라서 기존 예시의 H-05처럼 6인 동시 재고와 갑각류 대응이 미확인인 후보는 `winner`가 될 수 없다. 두 조건을 공급자 또는 숙소에 확인한 뒤에만 `VERIFIED/BOOKABLE`로 승격한다.

## 19.7 Booking Readiness와 링크아웃 Saga

MVP는 결제·발권을 하지 않지만, 예약 가능한 계획을 책임 있게 넘겨야 한다. Booking Coordinator는 예약 행위를 대신하지 않고 의존성, 담당자, 만료, 대안을 관리한다.

```text
flight price/inventory verified
→ hotel room combination verified
→ activity/restaurant time slot verified
→ schedule final validation
→ booking checklist issued
```

각 항목은 `{status, owner, deadline, priceAsOf, expiresAt, fallbackIds, dependentNodeIds, proofUrl}`를 가진다. 링크아웃 예약이 실패·만료·가격 급등하면 의존 노드를 `STALE`로 만들고 다음 후보로 전환한다. 이미 예약된 항목을 변경할 때는 취소·재예약·보상 작업을 순서대로 표시한다. 예약 순서, 동시 예약 필요성, 취소 가능성을 그래프로 노출한다.

## 19.8 DateResolver와 출발지 기반 총비용

DateResolver의 후보 점수는 `airfareIndex`만으로 결정하지 않는다. 빠른 사전 견적의 항공, 숙박, 현지 교통, 주요 티켓, 재고 신뢰도, 휴관 위험, 성수기, 날씨 불확실성을 포함한 `estimatedTotalTripCostRange`를 사용한다. 해외 Pack은 참여자의 출발 권역·공항 도착 가능 시간창을 필수 입력으로 받아 집/출발지→공항 비용과 첫차·막차를 비교한다.

기존 부록 C.4의 `score` 1·2위 차이 0.07 예시는 토론 조건에 해당한다. 따라서 그 레코드는 `method: "debated"`, `debated: true`여야 하며, 이후 문서·fixture도 이 규칙을 자동 검증한다.

## 19.9 결과 UX·프라이버시·재실행

결과 화면의 우선순위는 일정표가 아니라 다음이다.

1. 내 하드 제약 충족 및 계획 품질 상태
2. 내 대리인이 지켜낸 조건, 양보한 조건, 그 대가로 얻은 보상
3. 후보별 실격·근거·불확실성·runner-up 차이·CC 실제 영향
4. 일정표와 예약 체크리스트
5. 선택형 전체 회의록

회의록 리플레이에는 `이미 완료된 AI 중재 기록`을 상시 표시한다. 기본은 즉시 전체 보기이며, 타이핑·pause 연출은 선택 기능이다. 공동 뷰는 최소 만족도·익명화된 우려·최종 배정만 보이고, 설문 원문, 건강·신념·예산 상세, 방 배정 선호와 개인 만족도 상세는 본인 전용 뷰로 분리한다.

Rerun 전에는 변경될 노드, 예상 비용·시간, 예약 취소 위험, 전후 만족도·예산·동선 diff를 보여준다. `DRAFT/PARTIAL/VERIFIED/BOOKABLE/BOOKED` 상태와 누락된 안전 검증을 명확히 표시하며, PARTIAL은 예약 행동을 유도하지 않는다.

## 19.10 LLM 비용·지연·품질 관측 계약

결정론적 제약 컴파일·점수·예산·검증은 코드가 담당하고, LLM은 구조화된 주장·대안·설명에 한정한다. 후보 원본 전체 대신 conflict-relevant 속성 diff와 evidence ID만 전달한다. 애매한 강도만 소형 분류기/규칙 이후 LLM으로 보낸다.

각 호출은 `{round, purpose, model, promptVersion, inputTokens, outputTokens, cacheTokens, toolCalls, latencyMs, cost, fallbackReason}`를 기록한다. 비용 목표는 모델·단가·입출력 토큰·캐시 할인·Batch SLA를 명시한 가정표와 p50/p95 실측으로만 갱신한다. 라운드별 token/tool/latency budget을 별도로 두고, 초과 시 안전 검증을 축약하지 않는다.

## 19.11 GitHub 협업·품질 기준

현재는 문서 저장소이므로 CI는 Markdown 구조·로컬 링크·핵심 설계 불변식·비밀값 패턴을 검사한다. 코드 도입 후 lint, typecheck, unit, schema/contract, provider fixture, deterministic replay, prompt regression/eval, build를 required check로 추가한다. 실제 API 호출은 PR 검사에서 금지하고 sandbox/nightly에서만 비용 상한과 함께 실행한다.

`main`은 보호 브랜치로 운영하고, PR 최소 1인 승인·필수 검사 통과·직접 push 금지를 GitHub 저장소 설정에서 강제한다. PR은 영향받는 Planning Graph 노드, 스키마/프롬프트 버전, 재현 방법, 비용/eval 변화를 명시한다. ADR·기여·보안·소유권 정책은 코드 착수 시 팀 합의로 추가하되, 실제 GitHub 계정이 확정되기 전 임의 CODEOWNERS는 등록하지 않는다.
