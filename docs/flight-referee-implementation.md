# 오는 길·가는 길: 항공 도메인 구현 계획

- 문서 버전: v2.0 / 2026-08-14
- 단계: 1단계 `오는 길·가는 길`
- 공통 계약: [에이전트 아키텍처](agent-architecture.md)

파일명은 기존 링크 호환을 위해 유지한다. 독립된 “항공권 심판 에이전트”를 만들지 않는다. 항공은 1단계에서 `CandidateEvidenceAgent → FactConstraintValidator → UserProxyAgent → CategoryArbiterAgent` 공통 파이프라인이 다루는 도메인이다.

## 1. 입력

- `TripCharter`: 목적지, 목표 페이스, `DateDecision`, 참여자 범위
- 출발지·접근 가능한 공항/역·출발 가능 시간창
- 개인 목표예산·절대상한·추가 지불 의향
- 이용 불가 교통수단, 접근성·수하물·시간대 제약
- 이전 계약: 1단계는 없음

방장은 항공·기차·버스·배를 미리 고르지 않는다. 날짜 역시 방장 값이 아니라 `DateResolver` 결과를 사용한다.

## 2. 날짜와 재고를 두 번 구분

### 0단계

가용 날짜, 박수, 시간대, 계절·휴관 위험, 확보된 대략 가격 범위로 `DateDecision`을 만든다. 실시간 좌석을 조회하지 못했다면 있다고 가정하지 않는다.

### 1단계

선택 날짜의 실제 운행, 가격, 그룹 좌석, 운임 조건, 수하물, 도착·출발 버퍼를 다시 확인한다. 모두 실격되면 사전 승인된 날짜 유연성 안에서만 `DateResolver` 대안을 검토한다.

## 3. 공급자 현실

현재 “별도 제휴·운영 승인 없이 즉시 사용” 기준의 공급자 목록에는 한·일 항공 live 좌석·운임 API가 없다.

| 공급자/경로 | MVP 지위 | 상태 상한 |
| --- | --- | --- |
| Amadeus test API | 선택적 개발 fixture·응답 구조 실험 | 운영 커버리지·가격 검증 전 `PROVISIONAL` |
| 항공사/OTA 사용자 링크 | 사용자가 직접 확인 | `NEEDS_USER_CHOICE` |
| TAGO 열차 일정 | 한국 도시간 운행 일정 보조 | 좌석·운임 미확인 시 `VERIFIED` 일정까지만 |
| 정적 Pack 가격 범위 | DateResolver의 탐색 보조 | `PROVISIONAL` |

Amadeus production을 무승인 공급자로 문서화하지 않는다. 실제 live inventory 공급자가 없으면 1단계 전체 계획을 `BOOKABLE`로 만들지 않는다.

## 4. 후보와 제안

`CandidateRecord`는 한 항공편·열차편·버스편 같은 원자 후보다. 실제 투표 단위인 `CategoryProposal`은 다음을 묶는다.

- 참여자별 출발지 → 공항/역 접근
- 왕복 또는 편도별 실제 편명·운행 시각
- 수하물·환승·입국·탑승 버퍼
- 개인별 부담액과 통화 변환 기준
- 첫날·마지막날 실질 활동 가능 시간
- 변경·취소 조건과 검증 만료시각
- 검증 근거·미확인 사실·대안

같은 `proposalSetVersion`의 2~4개 제안에 대리인이 명시 투표한다.

## 5. 기계 검증

`FactConstraintValidator`가 최소한 다음을 검사한다.

1. 편명·운행일·출도착 공항/역·현지 시간대
2. 출발지 접근과 첫차·막차·체크인/탑승 버퍼
3. 환승 최소시간과 공항 변경
4. 그룹 인원 좌석 또는 좌석 미확인 상태
5. 운임 총액, 수하물·좌석·결제 수수료 포함 여부
6. 각 참여자 부담액의 절대상한
7. 변경·취소 조건과 가격 유효기간

최저 예산자의 단일 상한을 그룹 전체 상한으로 복사하지 않는다. 공동 이동이라도 개인별 실제 부담액을 각자의 절대상한과 비교하고, 불균등 부담은 사전 위임 범위 안에서만 적용한다.

## 6. 공정성 선택

하드 제약과 실행 가능성을 통과한 제안에만 만족도를 계산한다. 개인 만족도에는 다음을 포함할 수 있다.

- 총부담액과 추가 지불 의향
- 총 이동시간·환승·수하물
- 출발·도착 시간대
- 첫날·마지막날 활동시간
- 접근성·피로·불확실성

선택은 `leximin`이며 단순 Maximin → 총합 → 양보 크레딧 가중을 사용하지 않는다. 양보 크레딧은 명시된 최종 동률에서만 본다.

## 7. 출력

정상 결론은 1단계 `CategoryDecisionContract`에 다음을 남긴다.

- 선택 `CategoryProposal`과 대안
- 참여자별 투표·만족도·양보
- 검증 영수증과 `validUntil`
- 공항/역·출도착·수하물·비용·취소 조건
- 다음 단계 의무: 거점 권역, 체크인 가능시간, 예산 잔여, 첫날/마지막날 슬롯
- `obligationsForNextCategory`

모든 안전한 제안이 실격되면 선택안을 만들지 않고 `NO_SAFE_DECISION`과 `blockReason`을 가진 차단 계약을 남긴다.

## 8. 하류 영향

선택 교통편의 공항·역·시각·가격이 바뀌면 최소한 다음을 재검사한다.

- 2단계 거점·숙소 체크인과 위치
- 3단계 첫날·마지막날 활동
- 4단계 식사 슬롯
- 5단계 공항/역 이동, 전체 일정, 예산

값을 제자리 수정하지 않고 새 계약 버전을 만든다.

## 9. MVP 검증 시나리오

1. 서울 출발 2인 오사카 여행에서 공항 접근비·시간까지 합친 두 제안을 비교한다.
2. 가격은 싸지만 마지막 열차를 놓치는 제안이 기계 검사에서 탈락한다.
3. 그룹 좌석 미확인 후보가 `BOOKABLE`로 올라가지 않는다.
4. 한 참여자의 절대상한을 넘는 부담 이전이 자동 적용되지 않는다.
5. 선택 편 변경이 2~5단계를 `STALE`로 만들고 연속성 검사를 재실행한다.

## 10. 구현 완료의 증거

문서·fixture·Amadeus test 응답만으로 live 항공 계획 완료를 주장하지 않는다. 실제 날짜의 운행·그룹 좌석·총운임·취소 조건을 공급자 응답으로 관찰하고, 동일 입력 replay가 같은 검증 결과와 계약을 만들 때 해당 범위를 검증 완료로 표시한다.
