# LLM 런타임 설정 — 언제, 무엇을 정하나

- **문서 버전**: v0.1 / 2026-08-13 · **상태: 초안. 원가 수치는 실측 전 추정**
- **상위 문서**: [agent-architecture.md](agent-architecture.md) · [development-and-deployment.md](development-and-deployment.md)
- **다루는 범위**: 에이전트 설정(모델·키·시스템 프롬프트)을 언제 확정하는지, 원가 상한을 어떻게 지키는지

## 1. 언제 하나 — Data Agent 다음, 심판 이전

에이전트 설정이 필요해지는 시점은 컴포넌트마다 다르다. 순서를 지키면 키가 없어도 앞 단계를 끝까지 검증할 수 있다.

| 단계 | 컴포넌트 | LLM | 키 필요 | 상태 |
| --- | --- | --- | --- | --- |
| 1 | `packages/data-agents` — 캐시·제공자 어댑터·정규화 | ✗ | ✗ | 착수 (게이트웨이·정책·픽스처 완료) |
| 2 | `packages/agents` 기반 — LLM 클라이언트·원가 원장·프롬프트 버전 | ✓ | **여기서 처음** | 미착수 |
| 3 | Supervisor | ✓ | ✓ | 미착수 |
| 4 | 심판 7종 | ✓ | ✓ (+ 여행 API 키) | 미착수 |
| 5 | 페르소나 에이전트 | ✓ | ✓ | 미착수 |

**첫 LLM 소비자는 Supervisor여야 한다.** 호출이 실패하거나 파싱이 깨져도 Orchestrator가 기본 위상 순서로 진행하도록 이미 설계되어 있다(agent-architecture 4.4). 즉 LLM을 처음 붙이는 자리로 가장 안전하고, 실패가 run을 죽이지 않는다. 심판은 LLM과 Data Agent를 **둘 다** 필요로 하므로 마지막이다.

## 2. 모델 배분 — 역할마다 다른 티어

`LLM_MODEL_SUPERVISOR` / `LLM_MODEL_REFEREE` / `LLM_MODEL_PERSONA`를 따로 둔 이유는 원가다. 한 방 실행에서 호출 수가 가장 많은 것은 페르소나이고, 판단이 가장 어려운 것은 Supervisor다.

| 역할 | 시작점 | 단가 (input / output, 100만 토큰) | 근거 |
| --- | --- | --- | --- |
| Supervisor | `claude-opus-5` | $5 / $25 | 디스패치 순서·재심 판정. run당 호출 수는 적고 판단 품질이 결과를 좌우한다 |
| 카테고리 심판 | `claude-sonnet-5` | $3 / $15 (2026-08-31까지 도입가 $2 / $10) | 후보 비교·팩트체크. 수치 계산은 코드가 하므로 추론 부담이 Supervisor보다 낮다 |
| 페르소나 | `claude-haiku-4-5` | $1 / $5 | 발화 3문장·`max_tokens` 120. 호출 수가 인원수만큼 곱해진다 |

이 배분은 **시작점이지 확정이 아니다.** 품질이 부족하면 티어를 올리는 것이 먼저고, 원가는 3장의 두 장치로 흡수한다.

주의할 API 변경 사항:

- `temperature` · `top_p` · `top_k`는 최신 모델에서 **거부된다(400)**. 톤·다양성은 프롬프트로 조절한다. 페르소나 협상 스타일 4종(주장형/조정형/실속형/관조형)을 온도로 흉내 내려던 설계가 있다면 프롬프트로 옮겨야 한다.
- 추론 깊이는 `thinking: {type: 'adaptive'}` + `output_config.effort`(`low`~`max`)로 조절한다. 고정 토큰 예산(`budget_tokens`)은 제거됐다.
- `claude-opus-5`는 **thinking이 기본 켜짐**이다. `max_tokens`는 thinking과 응답 텍스트를 합쳐서 제한하므로, 응답 길이만 보고 잡으면 중간에 잘린다.

## 3. 원가 상한 $0.6를 지키는 두 장치

기획서 12장의 "배치 API로 40~50% 절감"은 실재하는 수치다. 다만 **배치만으로는 부족하다.**

### 3.1 Batch API — 토큰 단가 50% 절감

이 서비스는 완전 비동기다(사용자가 결과를 나중에 확인). 실시간 응답이 필요 없으므로 배치가 정확히 맞는 구조이고, 모든 토큰이 50% 단가로 계산된다. 최대 24시간이지만 대개 1시간 내 완료되며, run 상한 30분과 충돌하면 동기 호출로 폴백해야 한다 — **이 폴백 경로의 원가가 상한 계산의 실제 상단값**이다.

### 3.2 프롬프트 캐싱 — 라운드 내 공유 프리픽스

한 라운드에서 N명의 페르소나가 받는 컨텍스트는 대부분 같다(Pack 정보 + 하드 제약 요약 + 심판이 게시한 후보 카드). 이 공유 프리픽스를 캐시하면 두 번째 호출부터 해당 구간이 **읽기 0.1배** 단가로 계산된다. 쓰기는 1.25배(5분 TTL)이므로 같은 프리픽스를 2회만 써도 이득이다.

캐싱이 성립하려면 지켜야 할 것:

| 규칙 | 이유 |
| --- | --- |
| 공유 프리픽스가 **앞**, 개인 페르소나가 **뒤** | 캐시는 프리픽스 매치다. 앞이 1바이트만 달라져도 뒤가 전부 무효가 된다 |
| 프리픽스에 타임스탬프·요청 ID·UUID를 넣지 않는다 | 매 호출 프리픽스가 달라져 캐시 적중률이 0이 된다 |
| 도구 목록을 라운드 중간에 바꾸지 않는다 | 도구는 프롬프트 맨 앞에 렌더된다. 하나만 추가해도 전체 무효 |
| 모델을 라운드 중간에 바꾸지 않는다 | 캐시는 모델 단위다 |

**최소 캐시 길이가 모델마다 다르다** — 이게 티어 배분과 직접 충돌한다.

| 모델 | 최소 캐시 프리픽스 |
| --- | --- |
| `claude-opus-5` | 512 토큰 |
| `claude-sonnet-5` | 1,024 토큰 |
| `claude-haiku-4-5` | 4,096 토큰 |

페르소나를 `claude-haiku-4-5`로 돌리면 **공유 프리픽스가 4,096토큰을 넘지 않는 한 캐시가 아예 걸리지 않는다.** 오류도 경고도 없이 `cache_creation_input_tokens: 0`이 될 뿐이다. 후보 카드가 적은 라운드(R0·R6)가 특히 위험하다. 적중 여부는 응답의 `usage.cache_read_input_tokens`로 반드시 확인한다.

### 3.3 상한이 지켜지는지는 아직 모른다

거친 추정으로도 `RUN_COST_CAP_USD=0.6`은 빠듯하다. 라운드당 심판 4회 + Supervisor 2회 + 페르소나 12회, 입력 4~6K 토큰 기준으로 캐싱·배치를 **둘 다** 적용해야 겨우 들어온다. 캐싱이 안 걸리거나 배치가 폴백되면 넘는다.

따라서 다음을 Phase 0에서 실측한다.

- [ ] 라운드별 실제 입력 토큰 수 (`count_tokens`로 모델별 측정 — 토크나이저가 모델마다 다르므로 추정치를 재사용하지 않는다)
- [ ] 공유 프리픽스 길이가 페르소나 모델의 최소 캐시 길이를 넘는지
- [ ] 배치 완료 시간 분포와 30분 상한 초과율
- [ ] run당 총원가 실측 후 `RUN_COST_CAP_USD` 재설정

실측 전까지 상한은 **가드레일이지 예산이 아니다.** 초과하면 축약 모드로 강등하고(V6), 그 사실을 회의록에 남긴다.

## 4. 시스템 프롬프트 관리

| 항목 | 결정 |
| --- | --- |
| 위치 | `packages/agents/src/prompts/<agent>.<version>.ts` — 코드와 함께 버전 관리 |
| 버전 기록 | 모든 호출이 `llm_usage.prompt_version`에 남는다 (기획서 19.10) |
| 변경 절차 | 프롬프트 변경 PR은 영향받는 Planning Graph 노드와 재현/eval 결과를 명시한다 (README 개발·협업 기준) |
| 회귀 테스트 | C5·C7 판정 불일치율이 상승하면 프롬프트 회귀로 간주한다 (12.2 감시 지표) |
| 라운드 중 변경 | 금지. 프롬프트가 바뀌면 캐시 프리픽스가 무효가 되고 재현성이 깨진다 |

프롬프트에 **넣지 않는 것**은 계약으로 이미 정해져 있다(6.6): 제공자 원본 JSON, `rawPayloadRef` 내용, 다른 참여자의 설문 원문·방 배정 선호·건강·신념 상세. 이 경계는 Data Agent 응답 계층이 구조적으로 강제하므로 프롬프트에서 다시 막을 필요는 없다.
