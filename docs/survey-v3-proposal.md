## 1. 제안된 흐름

```text
[1] Setting   방장: 운송수단 · 여행지 · 페이스 · 예산 기준선   ※ 날짜는 정하지 않는다
[2] Concept   음식/액티비티/숙소 우선순위 → 식도락 / 호캉스 / 액티비티
[3] 세부 취향  사진 보고 중요도 선택 → 추가 항목 직접 입력 → 같은 중요도끼리 랭킹
[4] 토론      참여자 에이전트에 Concept·세부 취향 이식
[5] 사후      결과 보고 더 논의할 취향 체크 → 원하는 내용 입력 → 그 부분만 재토론
```

[5]는 이미 구현된 이의 제기와 같은 기능이다. [objection-and-rerun.md](objection-and-rerun.md)로 이미 정식화되어 있고, 부분 재토론(STALE 라운드만 재실행)도 동작한다. 설문 쪽에서 새로 만들 필요가 없다.

## 2. 점수 체계

| 라벨 | 점수 | 의미 | 스코어링 가중치 |
| --- | --- | --- | --- |
| `purpose` | 5 | 목적 — 이것 때문에 간다 | 1.0 |
| `preferred` | 3 | 선호, 협의 가능 | 0.6 |
| `whatever` | 1 | 아무거나 | 0.2 |
| `forbidden` | 0 | 불가 | **가중치 아님 — 실격 사유** |

`forbidden`을 "가중치 0"으로 처리하면 안 된다. 0점 후보도 총합이 높으면 선택될 수 있기 때문이다. 하드 제약으로 승격해 **스코어링 이전에 실격**시켜야 한다 (기획서 8.1).

동일 단계 내 랭킹은 보정으로만 쓴다. 보정폭(0.15)이 단계 간 간격(0.4)보다 작으므로 `preferred 1순위`가 `purpose 최하위`를 넘지 않는다. 이 순서가 뒤집히면 사용자가 단계를 고른 의미가 사라진다. 구현은 `deriveItemWeights()`.

### v2와 비교

| | v2 (현재) | v3 (제안) |
| --- | --- | --- |
| 취향 입력 | 슬라이더 12문항(1~7) + 카드 20장(1~10) | 4단계 + 동일 단계 내 랭킹 |
| 응답 부담 | 높음 | 낮음 |
| 해상도 | 높음 | 낮음 (랭킹으로 보완) |
| "불가" 표현 | 별도 섹션(절대 안 돼요) | 척도에 내장 |

v3의 장점은 **"불가"가 척도 안에 들어온다**는 점이다. v2는 "절대 안 돼요"를 별도 섹션에서 물어야 했고, 거기 적지 않으면 반영되지 않는 위험이 있었다(기획서 R3). 각 항목마다 불가를 표현할 수 있으면 이 위험이 줄어든다.

## 3. 컨셉 → 카테고리 가중치

| 컨셉 | dining | activity | accommodation |
| --- | --- | --- | --- |
| 식도락 `gourmet` | 0.50 | 0.25 | 0.25 |
| 호캉스 `resort` | 0.25 | 0.25 | 0.50 |
| 액티비티 `activity` | 0.25 | 0.50 | 0.25 |

이 가중치는 예산 배분(기획서 8.4)과 라운드별 만족도 가중에 함께 쓰인다. 참여자마다 컨셉이 다르면 **컨셉 자체가 R0의 협상 대상**이 된다. 다수결로 정하면 소수 컨셉이 전 일정에서 배제되므로, 개인별 가중치를 유지하고 Maximin으로 후보를 고르는 편이 정체성에 맞다.

## 4. 기존 설계와의 충돌 — 정리 필요

### C1. 방장이 날짜를 고르는가 (높음) — **결정: A안**

스케치의 Setting 단계에 날짜가 있었다. 그런데 기획서 v1.2는 **방장의 날짜 지정을 영구 제외**했다(14.2). 이유는 "방장이 정한 날짜"가 이탈의 주요 원인이고, 전원 가능한 구간을 계산하는 DateResolver가 그 대안이었다.

| 선택지 | 결과 |
| --- | --- |
| **A. 설문에서 수집 (채택)** | DateResolver 유지. 방 생성 30초. 전원 가능 구간 없을 때 완화 탐색 필요 |
| B. 방장이 확정 | DateResolver·`date_resolutions` 테이블·R0 일정 안건 삭제. 참석 불가자 처리 로직 필요 |
| C. 방장이 후보 2~3개 제시 → 설문에서 선택 | 절충. 계산은 줄고 방장 권한은 제한적 |

**A안으로 확정한다.** `roomSettingSchema`에서 `dateRange`를 삭제했다 — nullable로 열어 두면 언젠가 채워지고, 채워지는 순간 DateResolver는 우회된다. 스키마에 자리가 없어야 우회가 불가능하다.

사람이 날짜에 개입하는 지점은 하나만 남는다: **전원 가능한 구간이 없을 때**, 방장이 계산된 선택지(부분 참석 / 박수 축소 / 마감 연장) 중에서 고른다(기획서 3.3). 자유 입력은 여기서도 주지 않는다.

남은 구현: DateResolver(기획서 7.2)와 `date_resolutions` 기록, 그리고 확정 날짜가 없으면 R0를 시작하지 않는 게이트.

### C2. 예산을 방장이 정하는가 (중간)

스케치는 방장이 "개인 당 예산 한도"를 정한다. 기존 설계는 **참여자 각자의 상한을 설문에서 받고 그중 최저값을 그룹 상한으로** 쓴다(기획서 8.4, 항공 9.1). 항공은 전원이 같은 편에 타야 하므로 최저 예산자 기준이 절대적이다.

방장이 일괄 지정하면 예산이 빠듯한 참여자가 말할 기회를 잃는다. **방장 값은 기준선(baseline)으로 쓰고 개인 상한은 설문에서 따로 받는** 방식을 제안한다. 현재 `budgetPerPersonKrw`는 기준선으로 해석하고 있다.

### C3. 운송수단을 방장이 고르는가 (낮음)

스케치는 방장이 비행기/배 등을 고른다. 기존 설계는 R1 심판이 실효 총액으로 판정한다(항공 원칙 1). 방장이 "비행기"로 고정하면 심판은 그 안에서만 후보를 조달한다 — 판정 범위가 좁아지는 것이지 충돌은 아니다. 다만 `kr-*` Pack에서 "비행기"를 고르면 `kr-jeju`를 제외하고는 후보가 없다. **Pack의 `roundPreset`과 교차 검증이 필요하다.**

### C4. 개인 에이전트가 직접 웹검색·RAG를 하는가 (높음) — **결정: 하지 않는다**

스케치에 "개인에이전트가 정보탐색 에이전트가 추출한 데이터를 RAG로 가져오거나, 웹검색해서 가져오거나"가 있다.

**개인 에이전트가 직접 검색하면 그라운딩이 깨진다.** 기존 설계의 핵심 방어선은 "에이전트는 심판이 조달한 실제 후보 안에서만 논쟁한다"이고(기획서 1.3), 환각 한 번이면 신뢰가 회복 불가라는 전제가 있다(마무리 2번). 개인 에이전트가 각자 검색하면 세 가지가 발생한다.

1. 후보 밖 항목을 주장한다 → Validation Pass에서 `external_id` 검증 실패
2. 참여자 간 정보 비대칭이 생긴다 → 검색을 잘한 에이전트가 이긴다. 공정성 붕괴
3. 비용이 인원수만큼 곱해진다

**확정 형태**: 개인 에이전트는 검색하지 않는다. Data Agent가 캐시 DB에 쌓은 정규화 후보를 **심판이 조달**하고, 개인 에이전트는 그 후보에 대한 선호만 말한다. RAG는 Data Agent 계층에서 캐시된 데이터 위에 올린다 — 이게 스케치의 "핵심 해자"와 정확히 같은 구조다.

웹검색을 버리는 것이 아니라 **경로를 하나로 모은다.** 웹은 공식 API가 답하지 못하는 맥락(임시 휴업 공지, 축제 일정, 공사 안내)을 잡는 데 값어치가 있으므로, `web.search`·`web.page`를 다른 `queryClass`와 동일하게 심판 → Data Agent 경로에 편입했다. 다만 **advisory 전용**이다 — 캐시에 저장되고 회의록의 `uncertainties`에는 오르지만, 후보를 만들거나 `VERIFIED`·`BOOKABLE`로 승격시키지 못한다.

| 계약 | 코드 |
| --- | --- |
| `web.search` · `web.page` · `kb.retrieve` 추가 | `packages/contracts/src/data-agent.ts` |
| `persona:*` 호출 거부 (`callerId` 화이트리스트) | 같은 파일, `isAllowedCaller` |
| RAG 코퍼스 = `pack_cache` 정규화 payload, 만료 레코드 제외, `evidenceId` 동반 | [agent-architecture.md](agent-architecture.md) 6.9 |
| advisory 클래스는 fail-closed 검증을 대체할 수 없음 | 같은 문서 6.9 · 테스트 A21~A24 |

## 5. 핵심 해자 — 기존 설계와의 정합성

스케치의 해자 세 가지는 이미 문서화된 구조와 맞물린다.

| 스케치 | 대응 설계 |
| --- | --- |
| 내부 데이터가 쌓여 전처리 토큰 없이 재사용 | Data Agent의 `pack_cache` — 방 간 공유, Pack 단위 프리컴퓨트 (agent-architecture 6장) |
| 취향 데이터 축적으로 대리인 정확도 상승 | 아직 없음. **신규 설계 필요** (6장) |
| 여행 외 일반 의사결정으로 확장 | 아직 없음. **신규 설계 필요** (6장) |

## 6. 신규 설계가 필요한 것

### 6.1 취향 프로필 누적

현재는 방 단위로 설문을 받고 방이 끝나면 끝이다. 사용자 단위 취향 프로필을 누적하려면 다음이 필요하다.

- `user_preference_profiles` 테이블 — 방 간 누적, 카테고리별 중요도 이력
- 신규 방 진입 시 **이전 응답으로 프리필** → 설문 7분이 2분으로 줄어든다
- 여행 후 회고에서 실제 만족도를 수집해 프로필 보정 (기획서 15 Phase 2)
- 프라이버시: 프로필은 본인 것만. 방 참여자에게는 정규화 태그만 노출

이게 재방문 유인의 핵심이므로 T4·T3가 함께 설계할 값이 있다.

### 6.2 도메인 확장 (점심 메뉴 고르기 등)

현재 코어는 이미 도메인에 거의 독립적이다. 재사용 가능한 부분과 그렇지 않은 부분을 구분하면:

| 재사용 가능 | 여행 전용 |
| --- | --- |
| 중요도 척도·가중치 유도 | Destination Pack |
| Maximin 선택·양보 크레딧 | 라운드 R0~R6 구성 |
| Planning Graph STALE 전파 | 심판 7종의 판정 기준 |
| 이의 제기·부분 재실행 | 예약 준비·동선 최적화 |
| Supervisor 디스패치 프로토콜 | DateResolver |

"점심 메뉴 고르기"는 라운드 1개(dining) + Pack 없이 장소 후보만 있는 축소판이다. `roundPreset`을 확장 지점으로 이미 열어 두었으므로 구조 변경 없이 가능하다. **다만 MVP 범위는 아니다.**
